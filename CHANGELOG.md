# Changelog

SaaS OS releases (ADR-0015, "Release labels" and "One pull request per release"). Each entry names the exact commit; the newest names its release pull request until the next release writes in the SHA. Consumers pin that SHA, never the tag (`docs/CONSUMER-GUIDE.md` section 3). Upgrade steps are in `docs/CONSUMER-GUIDE.md` section 14. Each entry is also the body of the release's GitHub Release, which the Release workflow creates for the tag (`docs/RELEASING.md`); a GitHub Release is not a package publication.

## v0.11.0 (2026-11-12)

The merge commit of pull request #254, the release pull request (ADR-0015, "One pull request per release"). The next release writes its full SHA here. Until then, check that the tag `v0.11.0` resolves to that merge commit before pinning it, and with `git tag -v v0.11.0` that the owner's key signed it (ADR-0015 amendment of 2026-10-31). Previous release v0.10.0: `0f9bf4d67e13aff284af9f30505b7f256ea49801`.

It contains everything since v0.10.0 (`0f9bf4d`): pull requests #235 to #253 and this release. That is the governed AI inference follow-up programme, Gaps 20 to 22, stages 0 to 7 (ADR-0054 amendments of 2026-11-09 to 2026-11-11), a fix found by the pre-release check, a backend image fix and documentation. There are **six migrations** (the head moves from `e2b7c4d9a1f6` to `c7d2a9f4e1b6`) and **two new settings**, both optional with defaults that keep v0.10.0's behaviour. A minor release, not a patch: it adds public API, tables and permissions (ADR-0015, version numbers before 1.0).

**Support:** 0.11 is fully supported. 0.10 receives security and critical bug-fix support until 90 days after this release's GitHub Release `published_at`.

**Deployment steps (details in `docs/CONSUMER-GUIDE.md` section 14, "From v0.10.0 to v0.11.0"):**

- **Six migrations**, in this order: `c8e5a2f7d1b3` (platform AI hold), `b3d6f8a1c5e7` (index on attempts), `d2f7a9c4e6b8` (destination preference rank), `a4c8e1f3b7d5` (price units and review), `f1b9d3e7a5c2` (monetary AI budget) and `c7d2a9f4e1b6` (monthly AI usage rollup). Run `saas-os-migrate upgrade head`. **Run it at low traffic:** `c7d2a9f4e1b6` fills the rollup from the existing finished attempts while holding `control_plane.ai_inference_attempts` in `SHARE ROW EXCLUSIVE` mode, so AI requests that start or finish wait until it commits; reads do not wait (`docs/RUNBOOKS.md`, "AI usage reporting"). Checked on 2026-11-12 as a migrations role that is neither superuser nor `BYPASSRLS`: v0.10.0 to head in under 2 seconds with 4,500 attempts, the rollup equal to the attempts.
- **New permissions are granted to no role by SaaS OS.** Bind the ones you use: tenant `ai.usage:read` (usage and limits reads, the HTTP router) and `ai.budget:manage` (the tenant's own budget cap); platform `platform.ai_tenant_hold:manage` and `platform.ai_budget:manage` (operators).
- **The AI HTTP router is opt-in.** `build_platform_app()` does not mount it: `app.include_router(saas_os.api.v1.ai_usage.router)`.
- **Nothing else is required.** With no budget configured, no hold and the two settings unset, AI requests behave as under v0.10.0, except that a finished attempt is also counted in the monthly rollup.

**New settings:** `AI_PRICE_MAX_AGE_SECONDS` (whole seconds, `1` to `86400`, default `86400`) and `AI_INFERENCE_BUDGET_REQUIRED` (`true` or `false`, default `false`). Details in the stage 4 and stage 5 entries below.

**Backend image** (#237): the backend `Dockerfile` upgrades `zlib1g` to the Debian fix for CVE-2026-76844 and CVE-2026-85091 until a `python:3.13-slim` digest carries it. No code change.

**Additive public API** (compare `tests/architecture/public_api_snapshot.txt` with v0.10.0: two lines are added, nothing changes or goes): `saas_os.core.billing.entitlement_plan_ids` and `saas_os.core.platform_authority.run_tenant_platform_change` (stage 5). The AI functions listed in the entries below are in `saas_os.control_plane.inference` and `saas_os.api.v1.ai_usage`, outside the snapshot; their contract is `docs/architecture/AI-INFERENCE-CONTRACTS.md`.

**Tests only** (#250): the usage tests set their time window when each test starts. **Documentation only** (#235, #238, #240, #241, #243, #245, #247, #249, #252): the Gap 20 to 22 proposals with the owner's decisions (#235) and the gap register after each stage.

**Repository and release tooling:** no change to `scripts/release.py` or the workflows. `pyproject.toml` changed with #251 (one import-linter exception: `saas_os.api.v1.ai_usage` may import `saas_os.control_plane.inference.tenant_usage`) and with this release (the version).

**Known limits** (`docs/architecture/ai-gaps/GAP-REGISTER.md`): no retention purge of AI attempts (a decision on deleting records is open), no HTTP route for the monthly rollup read, and the bound for a month report over 1,000,000 attempts is not tested.

The example pins move to v0.10.0 (`0f9bf4d`), the previous release, as ADR-0015 requires (`docs/P-ROADMAP.md`, "Example pins moved to `0f9bf4d` (v0.10.0)"); the pinned-SHA install was checked for this move on 2026-11-12 (a clean Python 3.13 install of each example manifest from the pinned reference, import of `saas_os` and of the example's own package, version 0.10.0, installed commit `0f9bf4d`); the behavioural tests against it were not rerun. Migration head: `c7d2a9f4e1b6` (was `e2b7c4d9a1f6`). Before upgrading, read `docs/CONSUMER-GUIDE.md` section 14, "From v0.10.0 to v0.11.0".

**What changed, entry by entry** (the pre-release fix #253, then stage 7 down to stage 1; stage 1 is #236, 2 #239, 3 #242, 4 #244, 5 #246, 6 #248, 7 #251):

**Fixed: the downgrade of `f1b9d3e7a5c2` refuses stored tenant budgets under any migrations role** (pre-release check of 2026-11-12). Its guard counted the three tenant budget tables (`ai_tenant_budgets`, `ai_budget_periods`, `ai_budget_reservations`) under forced row-level security, where a migrations role that owns them but is neither superuser nor `BYPASSRLS` sees no tenant's rows: the guard passed and the downgrade dropped stored budgets. The downgrade now lifts FORCE on those tables first (the precedent of `e8f3b1d5a2c7`), in the same transaction that refuses or drops them. Upgrade unchanged; no released migration is affected (`f1b9d3e7a5c2` is unreleased).

**AI usage reporting: monthly rollup and HTTP surface** (Gap 22b, stage 7 of Gaps 20 to 22; owner decisions of 2026-11-09 and 2026-11-11; ADR-0054 amendment of 2026-11-11). **Migration `c7d2a9f4e1b6`** (head moves from `f1b9d3e7a5c2`).

- **New table `control_plane.ai_usage_monthly`**, tenant-owned under row-level security, `FINANCIAL_RETAIN`, no DELETE grant: per tenant, UTC month and grain (provider, model, use case, state, provenance, currency, unpriced), the counts and sums of finished attempts. Maintained by a trigger on `ai_inference_attempts` in the transaction that finishes an attempt; a deleted attempt stays counted. The migration backfills every finished attempt and holds the attempts table in `SHARE ROW EXCLUSIVE` mode while it does (attempt writes wait; see `docs/RUNBOOKS.md`, "AI usage reporting").
- **New reads** in `saas_os.control_plane.inference.tenant_usage`: `read_tenant_ai_monthly_usage` (whole UTC months from the rollup, at most 24, default the last twelve) and `read_tenant_ai_limits` (the soft token quota and the monthly budget). Same authority as `read_tenant_ai_usage`: `ai.usage:read`, users only.
- **Changed:** the `ai.usage.read` audit row's metadata gains `view` (`usage`, `monthly` or `limits`). Stage 2 is unreleased.
- **New opt-in router `saas_os.api.v1.ai_usage`** (not mounted by `build_platform_app()`, not re-exported by `saas_os.api.v1`): `GET /v1/tenants/{tenant_id}/ai/usage` and `GET /v1/tenants/{tenant_id}/ai/limits`, policy `ai.usage:read`, no API key. It is the one HTTP module allowed to import the AI Control Plane, and only the tenant usage read (import-linter `ignore_imports`).
- **Not changed or not included:** no retention purge of attempts and no rollup expiry (owner targets 90 days and 24 months stay unenforced); no route for the monthly read, model settings or budget management; no parent or descendant roll-up.

**Monthly AI budget warnings** (Gap 21c, stage 6 of Gaps 20 to 22; owner decisions of 2026-11-09 and 2026-11-11; ADR-0054 amendment of 2026-11-11). A budget can carry warning thresholds, whole percentages of its limit. The first time in a UTC month a tenant's estimated spend (settled, retained and reserved) reaches a threshold, SaaS OS sends a webhook event and writes an audit row. **No migration**, and nothing changes for a budget without thresholds; SaaS OS sets none by default.

- **Setting thresholds.** `set_plan_budget(..., warn_thresholds=[...])` (platform, `platform.ai_budget:manage`) and `set_tenant_budget_cap(..., warn_thresholds=[...])` (tenant, `ai.budget:manage`): 1 to 10 whole percentages from 1 to 100, strictly ascending (`invalid_thresholds` otherwise). The tenant's list replaces the plan's; an empty list turns warnings off. **A `set_tenant_budget_cap` call without `warn_thresholds` now clears the tenant's list** (back to the plan's): every call sets the cap and the list together.
- **New webhook event `ai.budget.threshold_crossed`**, the first event SaaS OS itself sends to a tenant's webhook subscriptions. `event_data`: `threshold_percent`, `period_start`, `currency`, `basis` (`estimated_platform_spend`); **no amount**. Subscriptions have no event filter, so every subscription of the tenant receives it: a webhook receiver must ignore event types it does not handle. Turning it into an email or an inbox item is the product's job.
- **New tenant audit action `ai.budget.threshold_crossed`**, attributed to the caller whose request reached the threshold, with the same fields and `trigger` (`admission` or `settlement`).
- **Once per threshold and month**, guarded by `ai_budget_periods.last_threshold_notified` in the same transaction. Checked at admission (counting the request's worst case, so a warning can precede the spend) and at a settlement above its reservation. A failed notification never fails the request; it is retried at the tenant's next request (`ai_budget_threshold_notification_failed` is logged).
- **Status.** `BudgetStatus` and the usage report's `budget` block gain the state `warning` and the fields `warn_thresholds` and `threshold_reached`. A stored threshold list that does not parse refuses as `budget_unavailable`.

**Monthly AI budget: reserve, then settle** (Gap 21b, stage 5 of Gaps 20 to 22; owner decisions of 2026-11-09; ADR-0054 amendment of 2026-11-10). A tenant can have a monthly budget of **estimated platform spend** in one currency, made of a billing plan's budget, an optional platform operator override and the tenant's own lower cap. Each provider attempt reserves its worst-case cost before anything is sent and settles its estimated cost afterwards, so parallel requests cannot together go past the budget. The budget limits the platform's own estimate (tokens times the operator's listed rates); it is not a provider invoice and the provider's invoice can differ (Gap 21 section 12). **A tenant with no budget runs exactly as before** unless the new setting `AI_INFERENCE_BUDGET_REQUIRED=true` is used.

- **One migration, `f1b9d3e7a5c2`** (the head moves from `a4c8e1f3b7d5`): five new tables and the widened platform permission CHECK. Global and platform-written (ADR-0056, `PROTECTED_TABLES`): `control_plane.ai_plan_budgets` (immutable budget versions per billing plan) and `control_plane.ai_budget_overrides` (one per tenant, with a closed reason and a required expiry). Tenant-owned under row-level security, application role without DELETE: `control_plane.ai_tenant_budgets` (the tenant's cap), `control_plane.ai_budget_periods` (one per tenant and UTC month: `reserved`, `retained`, `settled`) and `control_plane.ai_budget_reservations` (one per admitted attempt). No existing row changes. The downgrade refuses while any budget row or any grant of the new permission exists.
- **New platform permission `platform.ai_budget:manage`** (the vocabulary is thirty). It is placed in the bootstrap list, so a newly bootstrapped first owner holds it; an existing operator is never granted it automatically (`platform_bootstrap recover --grant platform.ai_budget:manage`, or a grant by a platform owner). Four new platform operations: `ai_plan_budget.configure`, `ai_budget_override.set`, `ai_budget_override.clear` (platform-configuration role) and `ai_budget_reservation.release` (application role, in the tenant's scope).
- **New tenant permission `ai.budget:manage`**, registered with the other AI permissions. Nothing grants it by default (a product binds it, ADR-0060); support access never satisfies it.
- **Admission.** In the transaction that starts each attempt, after the token quota and before anything is sent: the price of the attempt's model must be fresh (confirmed within 24 hours, `reviewed_at`) and in the budget's currency, and settled plus retained plus reserved plus this attempt's worst case must fit. Refusals are `InferenceQuotaExceededError` with the new reasons `monthly_budget_exhausted`, `budget_pricing_unavailable`, `budget_currency_conflict`, `budget_unavailable` and `budget_not_configured`; no attempt row is written and the provider is not called. The worst case counts one token per input byte at the highest input-side rate, plus `max_output_tokens` at the output rate, plus the amount per request, rounded up.
- **Settlement.** A budgeted attempt is priced with the price version it reserved with, not the one in effect at settlement. A definite provider refusal releases the reservation; a possibly accepted, interrupted, abandoned or unpriceable outcome keeps the worst case charged (`expired_unknown`, counted in `retained`) until a platform operator releases it with `release_budget_reservation` (audited in the tenant's and the platform's trails, one transaction). Usage the provider did not report settles the worst case.
- **New internal functions**, in `saas_os.control_plane.inference.budget_admin` (not added to `saas_os.inference`, whose surface stays pinned): `set_tenant_budget_cap` (`ai.budget:manage`, a user only, audited `ai.budget.set_cap`), `read_tenant_budget` (`ai.usage:read`, a user only, audited `ai.budget.read`), `set_plan_budget`, `set_tenant_budget_override`, `clear_tenant_budget_override`, `release_budget_reservation` (`platform.ai_budget:manage`). The usage report's `budget` block now carries the budget's state and amounts instead of always `unconfigured`.
- **Additive Core API**: `saas_os.core.billing.entitlement_plan_ids(tenant_id)` (the plan ids `get_entitlements` combines) and `saas_os.core.platform_authority.run_tenant_platform_change` (a platform change to one named tenant's rows, the outbox-replay pattern).
- **New deployment setting `AI_INFERENCE_BUDGET_REQUIRED`** (`true` or `false`, default `false` for compatibility; any other value is an internal error). The owner's rule is that it is ON in production whenever AI is enabled. With it on, a tenant whose plan has no budget and which has no override or cap is refused.
- **Operational duty that starts with this release.** A budgeted request is refused unless its model's price was confirmed in the last 24 hours, and every price that existed before `a4c8e1f3b7d5` has never been confirmed. Before giving any tenant a budget, confirm each price in use, and confirm it again at least daily (`docs/RUNBOOKS.md`, "AI model prices" and "AI budgets").
- **Not changed or not included:** warning thresholds and their events (Stage 6; the threshold columns are stored and unused); an automatic hold at exhaustion (owner decision 11: refusal only); any HTTP route or operator command; billing-anchored periods (UTC calendar month, like the token quota); currency conversion; the soft token quota, which is unchanged and still checked first. See `docs/architecture/AI-INFERENCE-CONTRACTS.md` section 7.4.

**AI price units and price staleness** (Gap 21a, stage 4 of Gaps 20 to 22; owner decisions of 2026-11-09; ADR-0054 amendment of 2026-11-09). A model price can carry a cache-write rate, an amount per request and rates for other billable units, and records when a platform operator last confirmed it. A price is current for at most 24 hours after that confirmation. **Nothing is refused on a price in this release**: the refusal for spend-controlled requests arrives with the spend limit (Gap 21b). Every cost here is an estimate of platform spend, never an amount a provider invoices.

- **One additive migration, `a4c8e1f3b7d5`** (the head moves from `d2f7a9c4e6b8`): four nullable columns on `control_plane.ai_model_prices`, `cache_write_per_million numeric(18,8)`, `per_request numeric(18,8)`, `unit_rates json` and `reviewed_at timestamptz`, and the check `ck_ai_model_prices_extra_units` (no negative rate; `unit_rates` is a JSON object). No default and no backfill: every existing price keeps its rates and gets NULL in the four columns. The table stays global and platform-managed, with unchanged privileges (the application role reads it, the platform-configuration role writes it, ADR-0056). Downgrading loses the new rates and the confirmation times and keeps every price. Run `saas-os-migrate upgrade head` before starting the new application and worker.
- **`set_model_price(..., cache_write_per_million=None, per_request=None, unit_rates=None, ...)`** in `saas_os.control_plane.inference.config.service` takes three new optional keyword arguments; existing calls are unchanged. `unit_rates` maps a billable unit name (`[a-z][a-z0-9_]{0,63}`, at most 16) to a rate per unit. Each rate is a `Decimal` from 0 to 1 000 000 with at most 8 decimal places. A new price is recorded as confirmed at the moment it is written. New refusals: `invalid_unit_rates`, `invalid_unit_name`.
- **`confirm_model_price(*, provider_key, model_id, pricing_version, caller, reason)`** in the same module records that an operator checked a price version against the provider's current price: `reviewed_at` becomes now and nothing else of the version changes (a different price is a new version). Needs `platform.ai_provider:manage`, like `set_model_price`; the change and its platform audit row commit together, and a call without the permission is recorded as `denied`. `ModelPriceView` (and so `read_ai_configuration` and `saas-os-operator ai-show`) carries the four new fields. Internal like every platform operation; **not added to `saas_os.inference`** (the public API snapshot is unchanged).
- **`price_status(price, *, at, max_age=None)`** and **`price_max_age()`** in `saas_os.control_plane.inference.accounting` classify a price as `fresh`, `stale` (confirmed longer ago than the limit), `unverifiable` (never confirmed, or confirmed in the future) or `missing`. The limit is 24 hours. **New deployment setting `AI_PRICE_MAX_AGE_SECONDS`** (whole seconds, `1` to `86400`, default `86400`) can shorten it and never lengthen it. No request reads the status or the setting in this release.
- **Behaviour change: an unpriced unit means an unknown cost.** An attempt that reports cache-write tokens under a price without a cache-write rate now records no cost (`estimated_cost` NULL, counted as cost unknown in the usage report) where it recorded an estimate that left those tokens out. A price with `per_request` adds that amount to each settled attempt. Neither happens without operator action: SaaS OS sends no cache-control instruction to a provider, and no existing price has the new rates.
- **After the upgrade, every existing price is `unverifiable` until it is confirmed.** That changes nothing in this release. Before the spend limit is used, confirm each price in use and keep confirming it within the limit (`docs/RUNBOOKS.md`, "AI model prices").
- **Not changed or not included:** no budget, reservation, warning or event (Stages 5 and 6); no refusal on a stale, unconfirmed or missing price; the soft monthly token quota; cached-input pricing; the rounding of an estimate (half up at eight decimal places); no operator command and no HTTP route for prices; no adapter reports a unit other than tokens, so `unit_rates` changes no recorded cost yet. See `docs/architecture/AI-INFERENCE-CONTRACTS.md` section 7.3.

**Tenant model eligibility, ranking and grant-time validation** (Gap 20a, stage 3 of Gaps 20 to 22; owner decisions of 2026-11-09; ADR-0054 amendment of 2026-11-09). A tenant can see which catalogue models it may use and why not, order the models it granted, and can no longer grant a model the platform's own policy would never allow.

- **One additive migration, `d2f7a9c4e6b8`** (the head moves from `b3d6f8a1c5e7`): a nullable `preference_rank smallint` on `control_plane.ai_tenant_destination_grants`, a `>= 0` check and a partial unique index over non-NULL ranks per tenant and use case. No default and no backfill: every existing grant stays unranked, which is today's behaviour. Downgrading loses the ranks the tenants chose and keeps the grants.
- **`list_eligible_models(tenant_id, *, use_case, caller, alias=None, classification=None)`** in `saas_os.control_plane.inference.eligibility`, internal; **not added to `saas_os.inference`** (the public API snapshot is unchanged). Needs `ai.policy:read`. Returns, per catalogue model, `granted`, `eligible` and a closed set of `blocked_by` reason codes in four families (unavailable, blocked, suspended, disabled). It uses the same checks as `run_inference`, so the two agree. It never returns an endpoint, a credential reference or a secret.
- **`set_destination_rank(tenant_id, *, use_case, provider_key, model_id, rank, caller)`** in `saas_os.control_plane.inference.config.tenant_policy`. Needs `ai.policy:manage`; writes an `ai.policy.set_rank` audit row in the same transaction. Among the models the tenant granted and an alias lists, `run_inference` tries the lower rank first and unranked grants after; a rank never adds a model to an alias and never makes an ineligible model eligible.
- **Behaviour change: `grant_destination` is stricter.** Enabling a grant that the evaluator would never allow is refused with `AITenantPolicyError("destination_not_eligible")` and the reason codes in `blocked_by` (model disabled or retired, classification not allowed by installation policy, or the tenant's own residency, retention or training-use requirement). A caller that granted a model the installation policy did not allow must now have the operator allow it first, or catch the error. Existing grants are untouched and are still checked at call time; disabling a grant is always allowed.
- **Not changed or not included:** no HTTP route (Stage 7); no change to the platform hold, the usage report or any budget; `set_tenant_ai_preferences` does not refuse a requirement that excludes already-granted models (the view reports it). See `docs/architecture/AI-INFERENCE-CONTRACTS.md` section 7.2.

**Tenant AI usage read** (Gap 22a, stage 2 of Gaps 20 to 22; owner decisions of 2026-11-09; ADR-0054 amendment of 2026-11-09). A tenant user holding the new permission `ai.usage:read` can read their own tenant's AI usage: attempt counts, token sums, **estimated** cost per currency and the soft monthly token quota.

- **One additive migration, `b3d6f8a1c5e7`** (the head moves from `c8e5a2f7d1b3`): the index `ix_ai_inference_attempts_tenant_started` on `control_plane.ai_inference_attempts (tenant_id, started_at)`. No table, column, constraint, policy, privilege or row changes. A plain `CREATE INDEX` blocks writes to the attempts table while it builds; on a large table build it beforehand with `CREATE INDEX CONCURRENTLY IF NOT EXISTS` (the migration then finds it). Run `saas-os-migrate upgrade head` before starting the new application and worker.
- **New tenant permission `ai.usage:read`**, registered with the other AI permissions (`register_ai_permissions()`). Nothing grants it by default: a product binds it to roles (intended: workspace owner and admin). It is not implied by `billing.subscription:read` or `ai.policy:*`, support access never satisfies it, and service accounts and system purposes are refused.
- **`read_tenant_ai_usage(tenant_id, *, caller, since, until, group_by)`** in `saas_os.control_plane.inference.tenant_usage`, internal like the tenant policy service; **not added to `saas_os.inference`** (the public API snapshot is unchanged). Window `[since, until)` in UTC, at most 93 days, default the current UTC month; grouping by `provider`, `model`, `use_case`, `provenance`, `state` or `day`. Cost is a `Decimal` per currency, never summed across currencies; attempts with unknown usage or no price are counted, never treated as zero; provider-reported and estimated tokens are reported separately. No prompt, completion, credential, provider request id or stored decision is returned.
- **Evidence.** Each allowed read writes one `ai.usage.read` tenant audit row (window and grouping only) in the same transaction as the read; a refusal writes a `denied` row. An unknown tenant and a foreign tenant are refused identically.
- **Not changed or not included:** no HTTP route (Stage 7); no parent or descendant roll-up (out of v1); no budget (Gap 21; the budget block reports `unconfigured`); no retention period is promised; `GET /v1/tenants/{id}/usage` and the Core `ai.input_tokens` and `ai.output_tokens` metrics are unchanged. See `docs/architecture/AI-INFERENCE-CONTRACTS.md` section 7.1.

**Platform hold on one tenant's AI** (Gap 20b, stage 1 of Gaps 20 to 22; owner decisions of 2026-11-09; ADR-0054 amendment of 2026-11-09). A platform operator can stop a tenant's new AI requests for a `security`, `contractual`, `spending` or `operator` reason, whatever the tenant's own policy and model grants say.

- **One migration, `c8e5a2f7d1b3`** (the head moves from `e2b7c4d9a1f6`). It widens `ck_platform_grants_permission` to twenty-nine permissions and creates `control_plane.ai_tenant_holds` (global, platform-owned, empty): the application role can only read it, and the platform-configuration role (ADR-0056) writes it, with no `DELETE`. No row changes and no backfill: with no hold row nothing changes for any tenant. The downgrade refuses while a hold row or a grant of the new permission exists. Run `saas-os-migrate upgrade head` before starting the new application and worker.
- **New platform permission `platform.ai_tenant_hold:manage`** (the vocabulary is now twenty-nine). It is not implied by `platform.ai_policy:manage` and is never granted to an existing operator automatically. The first owner of a new installation receives it at bootstrap; on an existing installation grant it with `platform_bootstrap recover --grant platform.ai_tenant_hold:manage`.
- **Operator commands:** `saas-os-operator ai-hold-set --tenant <id> --hold-reason <security|contractual|spending|operator>`, `ai-hold-lift --tenant <id>` and `ai-hold-show --tenant <id>`. Setting and lifting are AI configuration writes: like `ai-provider-create` they need `PLATFORM_CONFIG_DATABASE_URL` in that one command's environment (ADR-0056). The same functions, `set_tenant_ai_hold`, `release_tenant_ai_hold` and `read_tenant_ai_hold`, are in `saas_os.control_plane.inference.config.hold`, which is internal like every platform operation. **Not added to the public facade `saas_os.inference`** (the public API snapshot is unchanged): the facade's boundary test pins exactly `run_inference` and `stream_inference` and forbids a configuration seam, so exporting the hold there is a separate decision (see the ADR-0054 amendment).
- **Behaviour a product sees.** A held tenant's `run_inference` raises `InferencePolicyDeniedError` with `reason == "tenant_ai_held"`, before admission and before any adapter call, even when the tenant's policy is enabled and granted; the tenant's audit log records the refusal. Toggling or re-granting the tenant's own policy does not lift the hold; only a platform operator can. An attempt already started when the hold commits completes and settles; no attempt, retry or fallback that starts after the hold commits runs. Holding an already held tenant (`already_held`) and lifting one that is not held (`not_held`) are refused with `AITenantHoldError` and change nothing.

When a consumer records an audit row for an event that a user initiated, it passes `initiated_by=None` to `record_in_transaction()` or `record_system_action_in_transaction()` (stored as `"unavailable"`); `append_event(..., initiated_by=...)` still accepts the user initiator. A consumer that does not fails on every attempt, so its outbox event is retried and then dead-lettered; replay it after fixing the consumer.

**New settings:** `OUTBOX_EXTERNAL_EFFECT_MARKERS` (#204; default `false`: when `true`, `TenantJobContext.external_effect()` commits a durable started marker before a consumer's external request). Turn it on only after both outbox migrations and once no older dispatcher or worker can claim events. No SaaS OS consumer calls `external_effect()` yet, and the retry branches that would use the marker are not built (#214 is open), so a marked attempt that is lost is dead-lettered (`CrashAfterStart:`), never retried; leave it off unless you have read `docs/architecture/OUTBOX-STARTED-MARKER.md`. `WEBHOOK_ALLOW_HTTP` changes its meaning when unset (above). `OUTBOX_LEASE_SECONDS` gains a lower bound (above).

**Behaviour a product sees:**

- **Outbox timing uses the database clock** (#192). Due-ness, leases, retry delays, `published_at` and replay compare and schedule on PostgreSQL's transaction time, not the application host's clock, so a skew between the two can no longer delay a new event or make a live lease look due. Rows scheduled by a skewed host before the upgrade keep their stored time.
- **Unknown outcomes are classified** (#197). `AmbiguousOutcomeError` and `ConfirmedNotSentError` are new in `saas_os.core.outbox`; `EmailMessage` has a new optional `idempotency_key`. SMTP, Resend and webhook behaviour on ambiguous sends is in `docs/CONSUMER-GUIDE.md` section 14, notes 5, 6 and 10.

Webhook deliveries through the egress proxy trust certifi only (a receiver with a private CA now fails TLS); an address with more than one mailbox or a non-`addr-spec` form raises `InvalidEmailAddressError`; a job handler past 300 seconds and an outbox consumer past 270 seconds are dead-lettered; legacy plaintext webhook secrets log `webhook_signing_secret_legacy_plaintext` on each delivery; a notification to an invalid recipient is dead-lettered at once. Audit rows store a rebuilt plain-JSON copy of the metadata you pass.

Changed signatures and dataclasses (compare `tests/architecture/public_api_snapshot.txt` with v0.6.0): `record_in_transaction()` takes `initiated_by` and `correlation`; `append_event()` takes `initiated_by`; `record_platform_event_in_transaction()` takes `entry_id`; `SystemCaller`, `EmailMessage`, `EventExecution`, `OutboxDispatchConfig`, `OutboxEvent`, `SystemJobContext` and `TenantJobContext` gain optional fields, all appended with defaults (construct them by keyword; the snapshot lists fields alphabetically). - **Webhook delivery: optional port allowlist** (#70). `WEBHOOK_ALLOWED_PORTS`, a comma-separated list. Unset, any port stays allowed, so nothing changes by default. Set, it is checked when a subscription is created and before every delivery.
