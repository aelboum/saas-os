# SaaS OS — Distribution & Consumer Architecture Investigation

Status: INVESTIGATION — no architecture decision is binding until promoted to an ADR (see §18). This document does not change `docs/ARCHITECTURE.md`, `pyproject.toml`, `alembic.ini`, or any other configuration; it is the sole artifact of this investigation phase.

**Implementation status**: the recommendations in §6/§7/§9/§11/§15/§18 were promoted to ADR-0015/0016/0017/0018 (all Accepted) and implemented in the SaaS OS packaging implementation phase that followed this investigation — see each ADR's own "Implementation Note" section for what shipped and any deviations. This document itself remains an unmodified historical evidence record, not a living spec.

Scope: this is a follow-on to the corrected Module & Integration Architecture audit (`docs/ARCHITECTURE.md` remains the accepted baseline; `docs/ARCHITECTURE-DISCOVERY.md` §20's "Dograh is a consumer of this platform, not part of it" is the governing principle that audit restored). That audit established *what* SaaS OS is (a reusable, business-domain-agnostic foundation) and *what it is not* (a monorepo containing Recharge/MarocAssist/LPG/AuraVox). This document answers the question that audit left open: *how does an independent SaaS project actually consume it, mechanically, for years, across many projects?*

Evidence labels used throughout: **Fact** (directly observed in this repository), **Inference** (conclusion drawn from that evidence), **Recommendation** (a proposed decision), **Open question** (needs a human decision before implementation).

## 1. Executive Summary

**Fact.** This repository is already halfway to being a distributable package without anyone having decided that on purpose. `pyproject.toml` declares `name = "saas-os"`, `version = "0.1.0"`, a `setuptools` build backend, and an explicit `[tool.setuptools] packages = ["core", "infra", "control_plane", "products", "contracts", "api"]`. It has been buildable as a `pip install`-able artifact since the packaging config was first written — nothing about "SaaS OS as a package" requires new tooling to exist; it requires deciding what belongs in the package and how it gets to a consumer.

**Fact.** Every one of the 18 existing Alembic migrations (`infra/db/migrations/versions/`) is hand-written, not autogenerated — `env.py` sets `target_metadata = None` by deliberate design, because `infra/db` is architecturally forbidden from importing `core` to build a shared metadata object. This single fact removes the biggest usual objection to splitting migration ownership across a package boundary: there is no shared autogenerate-diffing metadata object to fragment. Two independently-tracked, hand-written migration histories applied to one database is not a workaround here — it is the same authoring model the repository already uses, just split into two script directories instead of one.

**Recommendation.** Distribute SaaS OS as a **versioned Python package** (starting as a pinned Git/VCS dependency — zero new infrastructure — with a private package index as a later, explicitly-triggered upgrade, §7), consumed by each independent project's own repository, plus a **one-time scaffold** (Dockerfile/compose/CI/Alembic-env shell) a new project clones once and then owns outright. Database migrations are handled as **two independent Alembic environments** applied to one shared database (one shipped inside the `saas-os` package for `core.*`/`control_plane.*`, one owned entirely by the project for its own schema) rather than a single branched multi-root history — simpler to reason about, and sufficient because the package version pin already encodes the schema-compatibility dependency that a cross-branch Alembic dependency would otherwise exist to express. `products/` is removed from the distributed package entirely; if a working end-to-end example is wanted, it lives in a non-shipped `examples/` directory used only by this repository's own CI (§9, §14). The AI Control Plane ships as an in-process library each project imports and registers its own tools into — no centralized service, because nothing in this codebase today has a network surface for Core capabilities, and no requirement in this investigation's scope demonstrates one is needed (§11).

## 3. Requirements

Restated from the investigation brief, as constraints this analysis is judged against:

- A new SaaS project must be startable with minimal ceremony and immediately get Core capabilities (identity, tenancy, RBAC, billing, usage, audit, notifications, AI governance).
- Each project: own repo, own database, own deployment, own secrets, own business logic, own project-specific integrations, own release schedule.
- SaaS OS must never depend on a consuming project, in any direction, at any time.
- The model must remain manageable at roughly 5–20 concurrent independent projects, several possibly on different major SaaS OS versions simultaneously, some needing project-specific extensions.
- Database migrations must cleanly separate `core.*` (SaaS-OS-owned) from `<project>.*` (project-owned) inside one physical database per project, across both fresh installs and long-running upgrades.
- No premature infrastructure: no plugin framework, no centralized AI service, no shared multi-project database/runtime, no generic `integrations/` layer — unless this investigation demonstrates a concrete need.

## 4. Candidate Architectures

**A — Versioned Python package.** `saas-os` published with a semantic version; a project's own `pyproject.toml`/`requirements` pins it (`saas-os==1.2.0`). Consumption is `import core.rbac`, `import control_plane.orchestration`, exactly as any Python library is consumed. Matches this codebase's actual call style (in-process function calls, not RPC) with zero impedance mismatch.

**B — Git/VCS dependency.** Same consumption model as A, but the package is never published to an index — a project's dependency manifest points directly at a Git URL and ref (`saas-os @ git+https://github.com/aelboum/call-agent@v1.0.0`, or a specific commit SHA). `pip` supports this natively; no registry infrastructure exists or is needed.

**C — Project template / scaffold alone.** A new project starts by cloning a template repository (Dockerfile, compose file, CI skeleton, `api/main.py` shell, Alembic env) that *copies* SaaS OS's source into the new project at creation time, with no ongoing dependency relationship afterward.

**D — Template + package.** The template provides the deployable shell (Dockerfile, compose, CI, Alembic env-wiring); the actual Core/Infra/Control-Plane/Contracts code is consumed as a real dependency (A or B), not copied. The project owns the shell outright from day one and can diverge from later template versions without that affecting its SaaS OS dependency.

**E — Monorepo.** SaaS OS and every consuming project's code live in one repository (this repo, with `products/recharge/`, `products/marocassist/`, etc., or a sibling `projects/` root). Already rejected by the prior audit (`docs/ARCHITECTURE.md`'s in-repo `products/` premise is exactly what that audit found inconsistent with the independent-project model) and re-evaluated here only for completeness.

**F — Git submodule.** A project's repository embeds `saas-os` as a Git submodule at a pinned commit, imported from a local path rather than an installed package.

**G — Shared SaaS OS runtime/API.** SaaS OS runs as one centrally hosted service; every project calls it over HTTP/gRPC for identity, tenancy, billing, usage, RBAC, and AI governance, instead of importing any code.

**H — Other.** Considered and rejected without a dedicated evaluation row: a compiled/wheel-only distribution (no advantage over a source package for a pure-Python, non-performance-critical codebase); a Nix/Bazel-style hermetic build system (large adoption cost, no problem in this codebase it solves that pip/setuptools doesn't); a "fork SaaS OS per project" model (defeats the entire purpose — every upstream fix would need manual re-application per fork, the exact opposite of "evolve independently over many years and many projects").

## 5. Detailed Comparison

**Fact/Inference**, argued from this codebase's actual shape (a synchronous-call Python monolith, not a service mesh):

- **A vs. B** differ only in *where the package is fetched from*, not in the consumption model — both are the same import-based dependency. B is strictly a lower-infrastructure starting point for A: a project's manifest can be repointed from a Git ref to a real index entry later with a one-line change, with zero code impact. There is no reason to choose A over B *today*, and no reason B can't evolve into A later.
- **C alone** fails the "evolve independently over many years" requirement outright: a template copy has no update mechanism. A security fix to `core.identity`'s OIDC handling would need to be manually re-applied, file by file, to every one of 5–20 projects. This is the failure mode the whole investigation exists to avoid.
- **D** solves what C alone cannot, by separating "things a project owns outright and customizes freely" (the deployable shell) from "things a project depends on and upgrades" (the actual platform code) — the shell doesn't need versioning discipline because it's copied once and immediately becomes the project's own file, no different from any other scaffold-generated boilerplate (a Next.js `create-next-app` output, a Django `startproject`).
- **E (monorepo)** was already rejected on architectural grounds (products' business logic must not share a repo, CI pipeline, or release train with the platform or with each other) and additionally fails this investigation's "own release schedule" requirement by construction — one repo has one release history.
- **F (submodule)** provides no capability A/B don't, while adding submodule-specific operational friction (detached-HEAD footguns, `git submodule update --init` steps every clone/CI run must remember, no dependency-resolution semantics for transitive requirements) for zero benefit over a normal pinned package dependency. Rejected.
- **G (shared runtime/API)** is the only option that would require *building new capability that doesn't exist* — every one of `core.rbac.can()`, `core.billing.get_entitlements()`, `core.usage.ingest_event()` etc. is an in-process Python function call today, with no serialization boundary, no network auth model between "the service" and "a project," and no multi-tenant-across-projects request routing. Building that is a materially larger undertaking than anything else evaluated here, and nothing in the stated requirements demands it — "own database, own deployment" per project is actually *easier* to guarantee with G rejected (each project's own deployment holds its own data; there is no shared service to accidentally leak across a project boundary in the first place).

## 6. Database Migration Analysis

This is the requirement most likely to be gotten wrong, so it gets the most scrutiny.

**Fact.** `infra/db/migrations/env.py`'s `target_metadata = None` is a deliberate, documented consequence of the dependency rule (`infra` must not import `core`). Every migration file so far is hand-authored DDL — nothing in this repository's history has ever used `alembic revision --autogenerate` against a real model registry. This matters directly: the usual argument against splitting an Alembic history ("autogenerate needs one `Base.metadata` to diff against") does not apply here, because autogenerate was never in use to begin with.

**Recommendation — two independent Alembic environments, not one branched multi-root history.**

```
Project X's database (one physical Postgres database)

  core.*, control_plane.*          ← schema owned by SaaS OS
      tracked by: alembic_version_saas_os
      script directory: shipped inside the installed saas-os package
                         (e.g. site-packages/infra/db/migrations/versions/)
      applied by:  saas-os's own migration entrypoint, invoked by the
                   project (e.g. `python -m saas_os.migrate` or an
                   equivalent console-script the package exposes)

  project_x.*                       ← schema owned by the project
      tracked by: alembic_version (the project's own, default name)
      script directory: the project's own repo
      applied by:  the project's own `alembic upgrade head`, exactly as
                   it already runs alembic today for its own tables
```

Two separate `alembic.ini`/env configurations, two separate version-tracking tables (Alembic's `version_table` option makes this trivial — it is not a hack, it is a documented, supported configuration key), applied as two separate commands in the same deploy step. No branch labels, no multi-head merges, no shared `alembic_version` row for two unrelated histories to collide over.

**Why not single-history multi-root (Alembic's built-in branch/`version_locations` support)?** It is a real, supported Alembic feature, and was seriously considered. Rejected as the *default* recommendation because it requires a project's Alembic environment to resolve a script directory living inside an installed package (solvable, but an extra layer of path resolution most teams have not had to reason about) and because it uses Alembic's branch-label/multiple-heads mechanism, which is one of the library's least commonly exercised features on most teams — it produces a strictly more general capability (a project migration can formally declare "depends on core revision X") that this investigation's requirements do not need: **the package version pin already encodes that dependency**. If a project's `pyproject.toml` pins `saas-os==1.4.0`, that pin already means "core schema as of 1.4.0's shipped migrations" — an explicit `down_revision` cross-branch pointer would express the same fact through a second, redundant mechanism. Two independent environments is the simpler design that satisfies the same requirement with one fewer moving part; it remains available as a later escalation if a real project ever needs to express "my migration N only makes sense after core migration M specifically, independent of overall package version" — a need this investigation found no evidence for.

**Fresh install.** A new project runs its scaffold's bootstrap step, which runs `saas-os`'s bundled core migrations against an empty database, then its own migrations. Order matters only in the sense that core tables (e.g. `core.tenants`, for any FK a project table takes into it) must exist first — a documented two-step bootstrap script (not a new mechanism, just an ordering convention) covers this.

**Upgrade (existing project, minor/patch SaaS OS bump).** Project bumps its `saas-os` pin, its dependency manager pulls the new package version (which includes any new core migration files), the project's deploy pipeline runs the core-migration command (applies only the new revisions, same as any Alembic `upgrade head` against an existing tracked history) then its own migration command as normal. No coordination with any other project is required, because each project's database and version-tracking table are entirely its own.

**Upgrade (major, breaking SaaS OS version).** A major bump may include a migration that changes an existing `core.*` table shape in a way incompatible with how an older `core.*` consumer's code queries it. The package's own semantic-versioning discipline (§8) is what protects a project here: a project does not have to move to the new major version until it is ready, and can run the previous major's migrations indefinitely on its own schedule — nothing about the two-environment migration mechanism forces synchronized upgrades across projects.

**Rollback strategy.** Identical to the repository's current model, applied per-environment: each hand-written migration should have a real `downgrade()` (the existing convention already does this — verified across the 18 existing revisions), so a bad core-schema upgrade rolls back with `alembic downgrade -1` scoped to the core environment only, without touching the project's own migration state.

**Conflict prevention.** Structurally impossible for the two histories to collide, because they never share a version-tracking table, a script directory, or (per the DB-ownership rule already established) a table namespace (`core.*` vs `<project>.*`). The only coordination discipline required is operational, not architectural: a deploy pipeline must remember to run *both* migration commands, in the right order, every time. This is the one real new operational risk introduced (§16 flags it as a risk, not a blocker) — mitigated by shipping the two-step bootstrap/upgrade script as part of the scaffold template (§9), so a project's deploy pipeline calls one script that runs both, rather than relying on a human to remember two commands.

**CI testing.** This repository's own `migrations` CI job (a disposable `postgres:16-alpine` service container, already in place) is the template for what a consuming project's own CI should do: spin up a throwaway Postgres, run the core-migration command from the pinned `saas-os` package, run the project's own migrations, assert both succeed. Cross-project migration testing (proving *every* consumer's migrations still apply after a new SaaS OS release) is a §14 testing-strategy question, not a mechanism question — covered there.

**Multiple SaaS OS versions across different projects.** Trivial under this model: each project's own Python environment has its own installed `saas-os` version and therefore its own copy of that version's core migration scripts. There is no shared migration-tracking state anywhere for two projects to conflict over, because there is no shared database.

## 7. Packaging/Distribution Analysis

**Fact.** No PyPI account, private index, or GitHub Packages configuration exists today. `pyproject.toml` already has everything a package needs to be `pip install`-able except a place to install *from*.

| Option | Fit for this team/stage |
|---|---|
| Public PyPI | Wrong — this is proprietary code (`license = "UNLICENSED"` already set); public PyPI is not access-controlled per-consumer. |
| Private PyPI-compatible index (e.g. self-hosted `simple` index, or a hosted option) | Real capability (auth-gated installs, standard `pip install` UX, proper release metadata) at real ongoing infrastructure cost (hosting, auth, publish CI step) — appropriate once there are enough projects/developers that "which Git ref am I even on" becomes a recurring source of confusion, not before. |
| GitHub Packages (or GitHub Releases + direct URL install) | A lower-cost middle ground — reuses the repository's existing GitHub hosting and access control (the same permissions that already gate this repo), still requires a small publish-on-tag CI step, but no separate service to run or pay for. |
| Direct Git/VCS dependency (a pinned tag or commit SHA) | **Recommended starting point.** Zero new infrastructure — pip's native `git+https://` dependency syntax, already usable with the existing GitHub repo and its existing access control, no publish step beyond tagging a release. |
| Template repository | Not a packaging channel by itself — this is the scaffold half of the recommendation (§4-D), not an alternative to A/B for the code half. |
| CLI-generated scaffold | A refinement of "template repository" (a `saas-os new my-project` command that generates the shell instead of a plain `git clone` of a template) — worth doing once the shell's shape has stabilized against at least one real project; premature to build before that. |

**Recommendation.** Start with a pinned Git/VCS dependency (zero infrastructure, matches this repo's existing "avoid premature infrastructure" pattern visible in ADR-0007's deferred workflow engine, ADR-0010's deferred Kubernetes, ADR-0012's deferred Vault). Move to GitHub Packages or a private index only when the number of active consuming projects and contributors makes "which commit SHA are we even pinned to" a recurring, real friction point — not on a schedule, on evidence.

## 8. Upgrade Analysis

**Recommendation.** Standard SemVer, covering the Python API surface, the database migration set, the Contract schema, and the AI Control Plane's registration API **as one coordinated release**, not independently versioned components. Rationale: these four things are shipped from one repository, tested together in one CI run, and a consuming project installs one version number for all of them — versioning them separately would let a project end up with, say, a Contract-schema version that assumes a Core-API shape the project's pinned Core version doesn't actually have, which is a worse failure mode than a single version number that's occasionally coarser than strictly necessary.

- **Patch/minor** (non-breaking additions, bug fixes, new optional Contract fields, new migrations that only add tables/columns): safe for a project to adopt whenever convenient; no coordination required.
- **Major** (a breaking change to any public `core.*`/`control_plane.*` interface, or a migration that alters an existing table in an incompatible way): requires the consuming project to read a changelog entry and explicitly decide to move; the project may stay on the previous major indefinitely, per its own schedule.

```
SaaS OS 1.0 → Project X created, pins saas-os==1.0.x
Project X evolves its own business logic, its own schema, on its own schedule
SaaS OS 1.1 released (non-breaking) → Project X bumps the pin whenever convenient,
    runs its own CI (unit/integration tests + the two-environment migration check,
    §6), deploys
SaaS OS 2.0 released (breaking) → Project X reads the changelog, decides whether
    and when to move; Project Y, on a different schedule, may move immediately;
    both are simultaneously valid, permanently — there is no shared runtime or
    shared database forcing them to agree
```

No project is ever forced onto a new major version by another project's decision, because nothing about this consumption model creates a shared resource (runtime, database, or otherwise) that would require agreement.

## 9. Repository Boundary Analysis

**Recommendation**, resolving the prior audit's flagged CRITICAL gap:

- `core/`, `infra/`, `control-plane/`, `contracts/` — **ship as the package**, unchanged in spirit from today's `[tool.setuptools] packages` list.
- `api/` — **ship the reusable parts** (the auth/tenant-resolution/health middleware and routers every consumer needs, e.g. today's `api/auth`, `api/health`, `api/middleware.py`, `api/dependencies.py`, `api/tenant_bootstrap.py`) as an importable router library a project mounts into its own FastAPI app, alongside its own product routes. This is a refinement, not a reversal, of today's packaging list — `api/` already contains no product-specific routes (only 3 route groups exist, none domain-specific), so nothing here needs to be cut, only re-framed as "a library a project's own `api/main.py` imports" instead of "the one process this repo itself runs."
- `products/` — **removed from the shipped package entirely.** Its premise (a real product's code living in this repo) is exactly what the prior audit found inconsistent with the corrected model. Drop it from `[tool.setuptools] packages`, from `pyproject.toml`'s `import-linter` `root_packages`, and from the `Dockerfile`'s `COPY` list.
- A **non-shipped `examples/reference-consumer/`** (new, not `products/` renamed) may exist in this repository purely as an internal testing fixture — exercising the package's public surface (identity+billing+usage+one AI tool, end-to-end) in this repo's own CI, explicitly excluded from `[tool.setuptools] packages` so it is never installed by a real consumer. This directly serves §14's "is one reference consumer project useful" question: yes, as a compatibility harness, never as a real product.

## 11. AI Control Plane Analysis

**Recommendation — per-project, in-process library instance. No centralized service.**

**Fact.** `control_plane.orchestration.ToolRegistry` is an in-process Python object today; nothing in this codebase exposes tool registration, invocation, or the three authorization gates (Tool/Data/Learning) over a network boundary. Building a centralized version would require: a new network-authentication model between a project's deployment and the central service, a way for the central service to reach a project-specific database or a way for the project to hand it tenant-scoped data over the network (reopening exactly the "malicious/untrusted external boundary" concern ADR-0013 exists to police, now applied to *SaaS OS's own consumers* rather than third-party AI providers), and a multi-project routing/isolation model that does not exist anywhere in this codebase.

**Recommendation detail.** Each project imports `control_plane` as part of its `saas-os` package dependency and runs its own instance of the `ToolRegistry`, in its own process, against its own tenant data. A project registers its own tools (e.g. Recharge's "check recharge status") from its own codebase, calling `core.rbac.register_permission()` (also its own in-process instance, backed by its own database) to declare the RBAC resource/action the tool needs — exactly the mechanism the prior audit already described, now confirmed compatible with a fully independent per-project deployment rather than requiring any shared runtime. Data Authorization and Learning Authorization gates apply identically, per project, with no cross-project state.

**This directly satisfies the investigation's instruction** ("do not assume a centralized AI service unless proven necessary") — nothing evaluated in this document demonstrates a need for one, and the per-project model is strictly simpler, cheaper, and more isolated.

## 12. Security Analysis

- **Supply-chain risk.** A Git/VCS dependency pinned to a mutable tag is weaker than pinning to an exact commit SHA (a tag can, in principle, be moved). **Recommendation:** pin consuming projects to a commit SHA (or, once available, a signed/immutable release artifact from a private index) rather than a bare tag name, for the same reason this repo's own `pyproject.toml` already pins dependency floors precisely rather than loosely.
- **No new secret-sharing surface.** Each project has its own `infra.secrets` instance, its own database credentials, its own OIDC client — nothing about package-based consumption introduces a shared secret store between projects or between a project and SaaS OS's own maintainers.
- **Migration privilege boundary** (already established, §2/§6): the migrations-role/runtime-role split (`MIGRATIONS_DATABASE_URL` vs `DATABASE_URL`) applies per project, unchanged — each project runs SaaS OS's shipped core migrations with its own privileged role against its own database, never a shared one.
- **Release signing/provenance.** Full supply-chain provenance tooling (Sigstore, SLSA attestations) is disproportionate to a small team at this stage — the same "avoid premature infrastructure" judgment already applied elsewhere in this repo's ADRs. A lighter-weight equivalent (commit-SHA pinning, a maintained changelog, code review on every release-tagged commit — all of which this repo's existing practices already approximate) is proportionate; full provenance tooling is an explicit non-goal for now (§19), revisit if/when a consuming project's compliance requirements demand it.
- **Project isolation.** Structurally total under this model (§10 of the prior audit, reconfirmed here): separate databases, separate deployments, separate secrets. There is no shared runtime for a security boundary to fail inside.

## 13. Testing Strategy

**Recommendation:**

- **SaaS OS's own unit/integration tests** — unchanged, already exist (`tests/core/`, `tests/infra/`, `tests/control_plane/`, `tests/contracts/`, `tests/api/`, `tests/architecture/`).
- **A reference consumer** (`examples/reference-consumer/`, §9) — the practical form of "contract tests" this investigation should recommend now: a minimal, non-shipped example project living in this same repo's CI that imports the package as if it were external, runs the two-environment migration flow (§6) against a throwaway database, registers one AI tool, and asserts the whole path works. This is Yes to §14's question, with the caveat that it is a CI fixture, never a real product and never distributed.
- **Migration tests** — the existing `migrations` CI job (disposable Postgres service container) is already the right shape; extend it to also run the reference consumer's own migrations after SaaS OS's, proving the two-environment ordering works end-to-end.
- **Cross-version compatibility matrix** (testing that Project-on-1.x and Project-on-2.x both still work) is explicitly **not** worth building until at least two real, independent consuming projects exist — before that point, there is nothing concrete to test compatibility against, and building the matrix speculatively risks exactly the "generic-but-useless abstraction" `docs/ARCHITECTURE-DISCOVERY.md` §23 already warns this codebase about. Deferred, not rejected (§20).

## 14. Decision Matrix

Scale: 1 = poor, 2 = weak, 3 = acceptable, 4 = good, 5 = excellent.

| Criterion | Package (Git/VCS) | Package (Private index) | Template alone | Package + Template | Monorepo | Submodule | Shared Service |
|---|---:|---:|---:|---:|---:|---:|---:|
| New project simplicity | 4 | 4 | 5 | 4 | 2 | 2 | 3 |
| Versioning | 4 | 5 | 1 | 4 | 1 | 3 | 4 |
| Upgrades | 4 | 5 | 1 | 4 | 1 | 3 | 3 |
| DB migrations | 4 | 4 | 2 | 4 | 3 | 3 | 2 |
| Isolation | 5 | 5 | 5 | 5 | 1 | 5 | 2 |
| Local development | 4 | 4 | 5 | 4 | 3 | 2 | 2 |
| CI/CD | 4 | 4 | 3 | 4 | 2 | 2 | 3 |
| Security | 3 | 4 | 3 | 3 | 3 | 3 | 2 |
| Maintenance (of SaaS OS itself) | 4 | 4 | 1 | 4 | 2 | 3 | 3 |
| 5–20 projects | 4 | 5 | 1 | 4 | 1 | 2 | 3 |
| Complexity (lower is simpler; scored so higher = simpler here) | 4 | 3 | 5 | 4 | 3 | 3 | 1 |

**Notes on the scores that most need explaining:**

- *Template alone* scores 5 on new-project-simplicity and local-development (nothing is simpler than a plain copy) but 1 on versioning/upgrades/maintenance/5–20-projects — a copy has no update path, which is disqualifying at any project count beyond one.
- *Monorepo* scores 1 on isolation and 5–20-projects deliberately — this is the option the prior audit already rejected on architectural grounds (shared repo, CI, and release train across unrelated businesses), reconfirmed here on purely operational grounds independently of that earlier reasoning.
- *Shared Service* scores lowest on complexity (1) because it is the only option requiring new capability to be built (a network API surface for Core, a cross-project auth model) rather than reusing what exists — and scores only 2 on isolation because a shared runtime is one misconfiguration away from a cross-tenant-across-projects leak, versus the structural (not configured) isolation every other option gets from separate databases.
- *Package (Private index)* outscores *Package (Git/VCS)* only on versioning/upgrades/maintenance/scale — reflecting that a real index is a strict improvement once justified, not that Git/VCS is deficient for the near term; §7 already recommends starting with Git/VCS and migrating later on evidence, not building the index now for a score improvement no one is positioned to use yet.

## 15. Recommended Architecture

Answering the brief's twelve required questions directly:

1. **What should SaaS OS distribute?** `core/`, `infra/`, `control-plane/`, `contracts/`, and the reusable parts of `api/` (auth/tenant-resolution/health middleware and routers) — as one versioned Python package.
2. **How should a new project consume it?** Pin it as a dependency (Git/VCS ref now, private index later) in its own `pyproject.toml`/equivalent, and clone a one-time scaffold for its deployable shell.
3. **What should be copied/generated once?** The scaffold: Dockerfile, docker-compose, CI workflow skeleton, the project's own `api/main.py` shell that mounts SaaS OS's routers alongside its own, and its own Alembic environment wired per §6.
4. **What should remain a runtime dependency?** Everything in (1) — imported, versioned, upgraded, never copied.
5. **How should migrations work?** Two independent Alembic environments against one database per project: SaaS OS's shipped core migrations (its own version-tracking table) and the project's own migrations (a separate version-tracking table) — §6.
6. **How should projects upgrade?** SemVer, one coordinated version number across API/migrations/contract-schema/AI-registration-API; minor/patch adopted whenever convenient, major adopted on the project's own schedule, never forced — §8.
7. **How should project-specific code work?** Entirely in the project's own repository; SaaS OS has no in-repo place for it (`products/` removed, §9).
8. **How should project-specific integrations work?** Same Protocol+Fake+adapter pattern SaaS OS already uses internally (Stripe, SMTP), authored in the project's own repository, never in a shared `integrations/` layer anywhere.
9. **How should AI Control Plane capabilities be consumed?** As an in-process library instance per project; each project registers its own tools against its own RBAC/data/learning gates — no centralized service, §11.
10. **What should happen to `products/`?** Removed from the distributed package (and from `pyproject.toml`'s packaging/import-linter lists, and the Dockerfile), §9. Optionally survives internally as a non-shipped `examples/reference-consumer/` CI fixture.
11. **What should the Product Contract become?** The schema/validator ships as part of the package as a self-description SDK surface a project fills in about itself; instances live only in consuming projects' own repos; three fields (`apiRoutes`, `frontendModules`, `deploymentRequirements`) are reframed from "shared-host registration" to "descriptive metadata," §10.
12. **What should we deliberately not build?** A centralized AI Control Plane service, a private package index (yet), a generic plugin framework, cross-version compatibility test infra, single-history multi-root Alembic branching, full release-provenance/signing tooling, a shared multi-project database or runtime — §16/§19.

## 16. Risks

- **Tag mutability** if a project pins a floating tag instead of a commit SHA — mitigated by the explicit SHA-pinning recommendation in §12, not yet enforced by any tooling.
- **Two-command migration discipline** — a deploy pipeline that runs only the project's own migrations and forgets SaaS OS's core migrations will silently drift. Mitigated by shipping the two-step bootstrap/upgrade script as part of the scaffold template (§6/§9), but this is a process discipline risk, not something the architecture itself prevents outright.
- **Zero real consumers today** means every recommendation in this document is untested against an actual second codebase — the reference-consumer CI fixture (§9/§14) narrows this risk but does not eliminate it; the first real project will surface friction this investigation cannot fully anticipate.
- **Long-term version sprawl** at 10+ projects on a mix of major versions is manageable per §8's reasoning, but places a real maintenance burden on whoever maintains SaaS OS itself — supporting N old majors indefinitely is a cost that should be bounded by an explicit support-window policy (an open question, §17), not left unstated.
- **Small-team support burden.** Once even one external-ish project depends on SaaS OS, changes to Core carry a support/communication cost (changelog discipline, breaking-change review) that did not exist when the repository had zero consumers — a real, ongoing cost this recommendation accepts as the price of reuse, not a reason to avoid it.

## 17. Open Questions

- What is the actual trigger threshold for moving from a Git/VCS-pinned dependency to a private package index — a specific project count, a specific pain point, or a calendar checkpoint? Not decided here; recommend revisiting when the second or third real project onboards, using their actual friction as evidence rather than guessing now.
- Should the Product Contract schema version independently of the rest of the package, or always move in lockstep (§8/§10)? Leaning lockstep, not decided.
- What is the intended major-version support window (how many old majors does SaaS OS's maintainer commit to keeping fixable/patchable)? Unaddressed by any existing doc; needed before the second project onboards onto a different major than the first.
- Should `infra/db/backup` (the backup/restore tooling) ship as part of the consumer-facing package, or remain a platform-team-only operational tool each project's own ops staff must reimplement or separately adopt? Not evaluated in this pass — flagged for the next one.
- Exact shape of the scaffold template (a plain `git clone`-and-rename starter repo vs. a `saas-os new <project>` CLI generator) — §7 recommends starting with the former and only building the latter once the shell's shape has stabilized against a real project; not designed here.

## 19. Explicit Non-Goals

Confirmed, with the reasoning this investigation found for each:

- **No `modules/recharge`, `modules/lpg`, or any domain-module directory inside this repo** — there is no in-repo module concept under the corrected model; a project's business logic is never SaaS OS's code (prior audit, reconfirmed).
- **No `projects/` containing real SaaS products** — same reasoning; only a clearly-labeled, non-shipped CI fixture is retained (§9).
- **No generic top-level `integrations/` layer**, in this repo or any consuming project's — integration is a pattern embedded in the owning module/project, proven twice already (Stripe, SMTP) and unaffected by the distribution-model question.
- **No shared multi-project database or runtime** — every option evaluated that would require one (Monorepo, Shared Service) scored worst on isolation in §14; separate databases per project is both the security boundary and the simplest mental model.
- **No SaaS OS → project dependency**, in either direction — the recommended package-consumption model makes this the only physically possible direction (SaaS OS's own `pyproject.toml` never lists a project as a dependency, and has no mechanism to import code it was never given).
- **No centralized AI service** — investigated directly in §11 and found unjustified by any current requirement or existing code.
- **No premature plugin framework** — §18; existing extension points (`register_permission()`, `create_flag()`, Provider/Protocol) are sufficient until a concrete case proves otherwise.
- **No implementation performed during this investigation, no commit, no push** — this document is the sole change made.
