# Staging: requirements, deployment and checklist

**Status (2026-10-31): prepared, not run.** No staging host exists yet, so nothing on this page has been executed against a real host. `scripts/deploy-staging.sh` and `deploy/staging-remote.sh` are covered by `tests/ops/test_staging_deploy_scripts.py`, which uses stubs for `ssh`, `docker`, `git`, `systemctl` and `stat`; that proves the order of the steps and every refusal, not a deployment. Production readiness stays NO-GO until the checklist below has run on a real staging host and every row has evidence (`docs/PRODUCTION-READINESS.md`).

SaaS OS is a library; each product deploys itself (`docs/CONSUMER-GUIDE.md` section 15). Staging here means the repository's **reference production stack** (`docker-compose.prod.yml`) on one disposable host, run so that the readiness gates that need a live deployment can be closed: 7, 10, 11 and 12, and the live provider and login checks.

## 1. What the owner provides

| Item | Requirement | Why |
|---|---|---|
| Host | One Linux VM, x86-64, 4 vCPU, 8 GB RAM, 60 GB disk; Docker Engine with Compose v2.17 or later (`up --wait`); `git`, `systemd`, `age` | The reference stack is Docker Compose on one host (ADR-0010) |
| Access | An SSH account for the operator, key-based only, in the `docker` group, allowed `systemctl start saas-os-backup.service`; the host key in the operator's `known_hosts` | `scripts/deploy-staging.sh` uses `ssh -o BatchMode=yes`: no password prompt, no key forwarding |
| Isolation | No production data, no production credentials, no network path to production databases or Redis | `docs/DEPLOYMENT-ARCHITECTURE.md` section 2 |
| Domains | Two DNS names for staging only, for example `staging.example.org` (`PUBLIC_DOMAIN`) and `id.staging.example.org` (`IDENTITY_PUBLIC_DOMAIN`), pointing at the host; ports 80 and 443 open | Caddy obtains the certificates (`docs/DEPLOYMENT-ARCHITECTURE.md` section 11) |
| Outbound network | HTTPS to `api.resend.com:443` and the AI provider through the egress proxy; the SMTP relay's port, if SMTP is used | Ledger rows 892, 893, 895 |
| SMTP relay | A relay reachable from the `internal` network, or Resend instead | Row 892 |
| Off-host storage | An S3-compatible bucket for staging only, with its own access key | Gate 11: restore from off-host storage |
| Restore target | A second, separate host or VM, used once, for the off-host restore | Gate 11 |
| Test credentials | Stripe **test mode** keys and webhook secret, a Resend key for a staging domain, one AI provider key with a spending cap | Gate 7 and the AI checks; placed by the owner on the host or in a secret store, never in the repository or a chat |
| Identity | The owner's account at the staging ZITADEL (created by the bootstrap) for the browser login | Row 1037 |

## 2. Secrets: created on the host, by the operator

No secret is generated by these scripts or kept in the repository. On the host, as the operator:

1. Clone the repository into the staging directory (for example `/srv/saas-os-staging`), from GitHub over HTTPS. Never copy a working tree from a developer machine.
2. `touch STAGING` in that directory. `deploy/staging-remote.sh` refuses any host without this marker, so the scripts cannot be pointed at a production checkout by mistake.
3. Create `.env` from `.env.example` and `.env.app` from `.env.app.example` (`docs/RUNBOOKS.md`, "Production configuration files"), then `chmod 600 .env .env.app`. The scripts check the mode and refuse 644; they never read the contents.
4. Generate the ZITADEL master key, its database password, the first-instance admin password and `ZITADEL_SESSION_COOKIE_SECRET` on the host, as `docs/RUNBOOKS.md` "Self-hosted identity operations" sections 1, 5a and 11 describe. These are staging secrets: never reuse them elsewhere, and never reuse a production value here.
5. Put the test credentials into `.env.app` only. Identity values never go into `.env.app` (`scripts/check-docker-prod-tls.sh` checks that).
6. Install the `deploy/*.service` and `*.timer` units with the staging paths (`docs/BACKUP-RESTORE.md`), and the off-host bucket's settings in `.env.app` (`BACKUP_*`).

## 3. Deploying

From a clone with `origin/main` fetched, on the operator's machine:

```
# 1. Plan: contacts nothing, prints the steps.
scripts/deploy-staging.sh plan --host op@staging.example.org --dir /srv/saas-os-staging \
    --commit <full sha> --first-deploy

# 2. First deployment (no database yet, so no backup).
scripts/deploy-staging.sh deploy --host op@staging.example.org --dir /srv/saas-os-staging \
    --commit <full sha> --first-deploy --confirm-host op@staging.example.org

# 3. Later deployments: backup first, then migrate.
scripts/deploy-staging.sh deploy --host op@staging.example.org --dir /srv/saas-os-staging \
    --commit <full sha> --confirm-host op@staging.example.org

# Rollback to the previous deployment, and a health check.
scripts/deploy-staging.sh rollback --host op@staging.example.org --dir /srv/saas-os-staging --confirm-host op@staging.example.org
scripts/deploy-staging.sh verify   --host op@staging.example.org --dir /srv/saas-os-staging --confirm-host op@staging.example.org
```

What the host script does, in order (and refuses before any change when a check fails):

1. Checks the `STAGING` marker, and that `.env` and `.env.app` are regular files with mode 600 or 400.
2. `git fetch`; refuses unless the commit is a first-parent commit of `origin/main`. A tagged release is reported as such by `plan`; an untagged commit is a candidate.
3. Checks out exactly that commit, detached; refuses local changes.
4. `docker compose -f docker-compose.prod.yml config --quiet`.
5. Backs up the database with `saas-os-backup.service` (skipped only on the first deployment, which is refused if a deployment is already recorded).
6. Builds, runs `saas-os-migrate upgrade head` with the migration role, and starts with `up -d --wait`, which fails if any healthcheck does not pass in time (`STAGING_WAIT_SECONDS`, default 300).
7. Records the deployed and the previous commit in `.deploy-state`.

**Rollback** checks out the previous commit, builds and starts it and waits for the healthchecks. It never downgrades the database: migrations are expand/contract (`docs/DEPLOYMENT-ARCHITECTURE.md` section 6), so the previous release runs on the newer schema. A rollback across a migration that breaks that rule is a restore from the backup taken in step 5 (`docs/RUNBOOKS.md`, "Platform operators", section 7).

## 4. Checklist

Each row closes, or partly closes, a readiness gate or ledger row once it has run with evidence. Record the date, commit, command and result in `docs/PRODUCTION-READINESS.md` and the ledger. Until a row is recorded there, it is not done.

| # | Check | How | Evidence to record | Closes |
|---|---|---|---|---|
| 1 | First deployment of a signed release | Section 3, step 2, with the release commit | `deploy` output; `verify` output; `.deploy-state` | Gate 12 (deployment) |
| 2 | ZITADEL at the patched version | `docker compose -f docker-compose.prod.yml images zitadel` after step 1 | Image tag and digest | Rows 1032, 1033 (HIGH) for this deployment |
| 3 | Identity bootstrap and master key | `docs/RUNBOOKS.md` "Self-hosted identity operations", sections 1 and 5a | `OIDC_CLIENT_ID` present; master-key file mode and owner | Gate 2, per deployment |
| 4 | Browser login | The owner logs in at `https://<PUBLIC_DOMAIN>` (or a Chrome-automated run, authorized separately) | Screenshot or log line of a session for the owner's subject | Row 1037 |
| 5 | Platform owner and first tenant | `docs/RUNBOOKS.md`, "Platform operators" section 2 and "First-tenant bootstrap" | Command output, audit rows | Gate 13 |
| 6 | Second deployment and rollback | Deploy a later commit, then `rollback`, then `verify` | Both outputs; the backup taken before the migration | Gate 12 (rollback) |
| 7 | Worker egress and email | Send one notification through Resend (or the SMTP relay); deliver one webhook to a test endpoint | Provider message id; delivery row `succeeded` | Rows 892, 893, 895 |
| 8 | Stripe test mode | `tests/core/billing/test_billing_stripe_integration.py` against the staging keys; one webhook from Stripe's test mode | Test output; the provider event recorded once | Gate 7 |
| 9 | One AI provider | `docs/AI-PROVIDER-QUALIFICATION.md` conformance run, within the spending cap | Conformance output | AI live checks |
| 10 | Backup timers as units | `systemctl list-timers 'saas-os-*'`; one run of each service | `journalctl -u` lines | Gate 11 (timers) |
| 11 | Off-host restore | Restore the latest off-host backup on the second host (`docs/BACKUP-RESTORE.md`), then the isolation checks of `docs/RUNBOOKS.md` "First-tenant bootstrap" section 12 | Restore output; isolation check output | Gate 11 (off-host) |
| 12 | Audit digest and external store | `docs/RUNBOOKS.md`, "Audit digests" sections 1 and 2 | Verification output | Row 924 |
| 13 | Alerting | Once an observability backend is chosen (ADR-0009): stop PostgreSQL for a minute and see the alert | Alert record | Gate 10 |

## 5. Tearing down

`docker compose -f docker-compose.prod.yml down -v` on the host, then delete the bucket's staging objects and revoke the staging test keys at each provider. Remove the `STAGING` marker last.
