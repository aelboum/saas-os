# Multi-Tenancy Architecture

Status: ACCEPTED. Isolation model finalized per `docs/ADR/0002-multi-tenancy-isolation-model.md`.

## 1. Tenant Model

- A **tenant** is a Core entity owned by `saas_os/core/tenancy`, identified by a stable `tenant_id`. **A tenant *is* the customer organization** — "tenant" and "organization" are the same entity, not two related entities. `tenant_id` is the canonical column/field name in every schema and internal interface; APIs and Product-facing UI may label it `organization_id` for end users, but there is exactly one ID and one table (`core.tenants`) behind both names. Do not introduce a separate "organization" entity anywhere in Core or Product.
- A **user** is a global identity (`saas_os/core/identity`), independent of any tenant, that holds zero or more memberships in tenants via `saas_os/core/rbac`-scoped roles. A user is never modeled as belonging to exactly one tenant.
- Every piece of tenant-owned data, in every layer and every Product, carries a `tenant_id` that traces back to `core.tenants`. There is no tenant-owned data without an explicit tenant reference.

## 2. Isolation Model (Accepted)

Per `docs/ADR/0002-multi-tenancy-isolation-model.md`:

- **PostgreSQL, shared database, shared schema, row-level tenancy** (`tenant_id` column on every tenant-owned table) for all tenants.
- **Enforced at the data-access chokepoint** (`saas_os/infra/db`), not by convention: every query that touches tenant-scoped data passes through a query layer that injects/validates `tenant_id` scoping.
- **PostgreSQL Row-Level Security (RLS) policies** on every tenant-owned table as defense in depth, keyed on a session-level `tenant_id` set by `saas_os/infra/db` at the start of each request/job — so a bug in application-layer scoping does not, by itself, leak cross-tenant data at the database level.
- A **hybrid escape hatch** (dedicated database per tenant) is architecturally anticipated for high-value or compliance-constrained tenants, without being built now — `saas_os/infra/db` resolves a tenant's storage location through an indirection, not a hardcoded connection, so this can be added later without changing calling code in Core or Product.

## 3. Enforcement Boundary

- **The single enforcement point is `saas_os/infra/db`.** No Core module, Product module, or Control Plane tool queries the database directly — all go through this layer, which requires a `tenant_id` (or explicit, logged "cross-tenant admin" override — see §5) on every tenant-scoped query.
- This is the concrete mechanism behind the security principle in `docs/SECURITY.md` §5: tenant isolation is a data-access-layer guarantee, not a per-query discipline every engineer (or AI agent) must remember.
- Code review and CI checks (Phase 1 of the roadmap) should flag any raw query construction that bypasses this layer. **This is now enforced, not only reviewed**: `tests/architecture/test_tenant_session_boundary.py` (`docs/ADR/0022-tenant-session-boundary-enforcement.md`) statically fails if a tenant-owned access path calls `saas_os.infra.db.session_scope()` (the untenanted entry point) instead of `tenant_session_scope()`, unless the call site is a curated, individually-reviewed global/system exception (the tenant registry, global identity/catalog tables, and the one documented `saas_os.core.api_keys` bearer-credential exception — see the ADR's own table inventory). RLS (§2) remains the actual runtime, database-level fail-closed guarantee; the architecture test is a static control layered in front of it, not a replacement.

## 4. Isolation Across Other Layers

Tenant isolation is not only a database concern:

| Layer | Isolation mechanism |
|---|---|
| Database | `tenant_id` scoping enforced at `saas_os/infra/db` (§3), RLS as defense in depth |
| Cache | Cache keys are namespaced by `tenant_id`; no shared cache key can serve two tenants' data |
| Job queue | Every job payload carries `tenant_id`; workers scope their data access identically to request-path code (same `saas_os/infra/db` chokepoint) |
| Object/file storage | Storage paths/buckets are namespaced by `tenant_id`; no tenant can be given a credential or path scoped broader than its own prefix |
| Logs/traces | Every log line and trace span carries `tenant_id` (see `docs/OBSERVABILITY.md`), but log/trace storage itself is not tenant-isolated infrastructure — access to observability tooling is a platform-operator concern, governed by RBAC, not a customer-facing isolation boundary |
| AI Control Plane | Every agent identity acting on tenant data is scoped to that `tenant_id`; a support or product agent cannot address a different tenant's data even if the underlying tool would technically allow it (see `docs/AI-CONTROL-PLANE.md`) |

## 5. Cross-Tenant Access (Platform Admin / Support)

- Any access that spans tenants (platform admin tooling, cross-tenant analytics, human support staff looking at a customer's data) is a **distinct, explicitly logged code path** — never the same code path as tenant-scoped access with the check silently skipped.
- Cross-tenant access is itself an authorized, audit-logged action (`docs/SECURITY.md` §8), attributable to a specific human or agent identity and, where the action is customer-data-sensitive, subject to the same approval-gate framework as AI Control Plane actions.
- **That code path exists, in two forms, and neither is tenant RBAC with a check skipped** (`docs/ADR/0045-installation-scoped-platform-authority.md`):
  - *Operational oversight* by a platform operator: an enrolled user of this deployment holding an explicit platform permission, decided by `saas_os.core.platform_authority.platform_can()` from platform grant storage only. It returns fixed, data-minimized projections (the tenant registry, a commercial overview, one tenant's flag overrides) and never a tenant's business data. Each read is authorized and audited with no tenant bound, enters a tenant scope only for one fixed query per named tenant, and leaves two rows in `core.platform_audit_log`, a table no tenant-scoped transaction can see. A tenant cannot opt out of it, and a suspended or deleted tenant is still listed. An oversight read is recorded in the platform audit only; a platform *change* to a tenant is also recorded in that tenant's own trail.
  - *Support access* to a customer's data: the tenant-approved, time-bounded request of `saas_os.core.rbac`. Platform authority does not grant it, shorten it or replace it.
- Platform authority and tenant authority do not convert into each other: a platform permission is not a row of the tenant permission catalog and cannot be attached to a role, delegated or denied; a tenant role, however broad, is never platform authority. In particular, a `SUBTREE` role at a root tenant that holds every customer is tenant authority over all of them, not platform administration, and is not a substitute for it.
- No platform query spans tenants' row-level-security-protected tables. Where a platform operation must find a user's memberships (`deactivate_user`), it visits the registry one tenant at a time under each tenant's own scope and returns no tenant data. Two tables are global by design and are read or written across tenants: the registry itself (`core.tenants`), and `core.api_keys`, where revoking a user's keys updates that one user's keys in every tenant in one statement.

## 6. Tenant Lifecycle

Owned by `saas_os/core/tenancy`. States: `pending` → `active` → `suspended` → `deleted` (soft, retaining audit trail) → `purging` → `purged` (a permanent, minimized tombstone — `saas_os.core.tenancy.lifecycle`, `saas_os.core.tenancy.purge_tenant()` — never a hard-deleted row; the tenant id can never be reused, so every retained record that references it, e.g. `saas_os.core.audit_log`, stays valid). Product modules do not maintain their own notion of whether a tenant is active — they read the tenant's current status through Core (`saas_os.core.tenancy.get_tenant()`), never a cached or locally-tracked copy of it.

**Core/Product purge responsibility (RA-12-2).** Core owns tenant lifecycle state and purge *orchestration*; a Product owns its own tenant-associated data and is responsible for its own purge *behavior* — Core does not know a Product's tables, and `saas_os.core.tenancy` never imports Product code (the dependency direction in §1 above is one-way: Product → Core, never the reverse). A Product that retains tenant-associated data requiring purge participates by registering a `saas_os.core.tenancy.purge_participants.TenantPurgeParticipant` — an explicit interface a Product implements and registers with Core, not an event subscription, since no tenant-lifecycle event bus exists in this codebase. `purge_tenant()` calls every registered participant once Core's own `PURGE_STEPS` have fully converged, still inside the same `PURGING` lifecycle fence those steps run under, so a participant never sees a live (`ACTIVE`/`SUSPENDED`/`PENDING`) tenant and never receives any tenant other than the one being purged. A participant's own purge must be tenant-scoped (it receives only the opaque tenant id being purged, never a database session or connection) and idempotent (Core may call it again on retry, including after a crash). A participant failure is fail-closed exactly like a Core step failure: the tenant is not transitioned to `PURGED` while any registered participant has failed, and the failure is recorded with the same bounded, opaque metadata Core's own steps use — a participant identifier and an exception *type* name, never its message or any customer content. A Product is not required to delete its data outright: it may instead register a participant that anonymizes or otherwise retains its own data under a separately documented, deliberately approved retention policy — this contract only makes *some* explicit, tested answer mandatory once a Product registers a participant, never which answer. Reference implementation: `examples/reference-consumer/reference_consumer/purge.py`.

**Individual identity erasure is a separate operation from tenant purge (RA-12-3).** `core.users` and `core.external_identities` are global identity data (`GLOBAL_IDENTITY` in `saas_os.core.tenancy.retention.RETENTION_CLASSIFICATION`) — a single `User` can hold memberships in many tenants, so `purge_tenant()` (above) never touches them, and no tenant's purge ever erases a person's identity. The independent mechanism for that is `saas_os.core.identity.erasure.erase_user_identity()`: given a `user_id` and the specific `tenant_ids` the caller wants checked, it first deletes every `core.external_identities` row of the user, in the transaction that checks the user is not an enrolled platform operator (ADR-0045 section 6, amended 2026-10-14), then removes that user's own membership (and everything that exists solely because of it — `saas_os.core.api_keys`, `saas_os.core.notifications`, `core.membership_roles` — in each named tenant, touching no other member's data and no tenant business data), then deletes every `core.sessions` row belonging to that user everywhere. `core.users.id` itself is never deleted (many `NOT NULL` foreign keys, e.g. `core.invitations.inviter_user_id`, make that schema-unsafe, the same reasoning that gives tenants their `PURGED` tombstone) but the row already carries no personal data, so nothing needs scrubbing. **Tenant discovery is the caller's responsibility**: `core.tenant_memberships` is RLS-protected, and this module does not introduce a privileged, RLS-bypassing lookup inside Core's business logic to enumerate a user's tenants for it — ops/admin tooling supplies `tenant_ids`, exactly as callers already supply the target to `purge_tenant(tenant_id)`. **Authentication**: once `core.external_identities` is deleted and committed, a later login with the same external `(issuer, subject)` provisions a genuinely new, unrelated `User` (the existing "not found" path in `get_or_create_user_for_external_identity()`) — it cannot resolve back to the erased identity, and every session that referenced it is already gone. **Retained records** (`saas_os.core.audit_log`, `core.support_access_requests`, billing/usage records, AI Control Plane tables) keep whatever `actor_user_id`/`*_by_user_id` reference they already had — valid because the `core.users` row still exists, and not a privacy issue because that reference is an opaque id, not a name or external subject; no `RETENTION_CLASSIFICATION` value changes. **Authorization**: this codebase has no platform-wide (cross-tenant) admin-authorization model to check against — `saas_os.core.rbac.can()` is inherently tenant-scoped — so, mirroring `saas_os/infra/db/backup`'s own "not an application-runtime capability" precedent, `saas_os.core.identity.erasure` is fenced at the import boundary (an import-linter contract forbidding `api`, `products`, and `control_plane` from importing it) rather than left to convention; every call still requires an existing `actor_user_id` (fails closed otherwise) so it is attributable, but verifying the caller is *authorized* to erase a given identity remains the trusted caller's own responsibility, exactly like `purge_tenant()`'s callers. **Idempotency and non-enumeration**: every step is a plain existence-scoped delete, so a nonexistent identity, one that was never a member of the given tenants, and one already fully erased all produce the identical all-zero result — a caller cannot distinguish them, and calling the operation again is always safe.

**Session retention and cleanup (RA-12-5).** `core.sessions` is global identity infrastructure, not tenant-owned data — no `tenant_id` column, no RLS policy, `GLOBAL_IDENTITY` in `saas_os.core.tenancy.retention.RETENTION_CLASSIFICATION` (unchanged). An expired or revoked session is already logically unusable the instant `saas_os.core.identity.sessions.validate_session()` rejects it (`SessionExpiredError`/`SessionRevokedError`) — this section's cleanup only bounds how long the resulting useless row stays physically stored in PostgreSQL; it changes nothing about whether a session can authenticate. `saas_os.core.identity.session_retention.cleanup_expired_sessions()` deletes a session row once it is **expired** (`expires_at < now()`, immediately, regardless of revocation state) or **revoked past a configured grace period** (`revoked_at` older than `SessionRetentionConfig.revoked_grace_period_seconds`, `saas_os/core/identity/config.py`, default 24 hours) — the grace period exists solely so a just-revoked session's row remains available for operational/security investigation for a bounded window; it is an application operational policy this repository has chosen, **not a claimed legal retention requirement**. Deletion runs in bounded, database-side batches (`SESSION_CLEANUP_BATCH_SIZE`, default 500 rows per statement) using `DELETE ... WHERE id IN (SELECT ... LIMIT ... FOR UPDATE SKIP LOCKED)`, so two overlapping cleanup runs skip each other's in-flight batch rather than blocking or double-deleting, and no batch ever loads full session rows into Python. The cleanup is registered as an ordinary ARQ job (`saas_os.core.identity.SESSION_CLEANUP_JOB_FUNCTIONS`, executed by the existing `saas_os.api.worker` process, `keep_result=0` like every other job here) and requires no tenant id and no tenant-membership discovery — it is not one of `saas_os.core.tenancy.PURGE_STEPS` and is never routed through `purge_tenant()`. Production triggers it periodically (`SESSION_CLEANUP_INTERVAL_SECONDS`, default 1 hour) via a host-level `systemd` timer (`deploy/saas-os-session-cleanup.timer` + `.service`, mirroring `deploy/saas-os-backup.timer`'s own "timer invokes a small Python entrypoint" mechanism) that runs `python -m saas_os.api.session_cleanup_trigger` to enqueue one job onto the existing Redis queue for the worker to execute — no new scheduling framework, and `saas_os/infra/jobs`/arq's own `cron_jobs` feature is deliberately not introduced since nothing else in this repository uses it. **This does not change identity erasure (RA-12-3)**: `erase_user_identity()` still deletes *all* of one specific user's sessions immediately via `purge_user_sessions()`, regardless of expiry or revocation state — the two mechanisms answer different questions ("erase this person now" vs. "stop storing rows nobody can use anymore, on a schedule") and neither weakens the other.

**Redis dead-letter cleanup on tenant purge (RA-12-7).** `purge_tenant()` now removes this tenant's own entries from the shared, cross-tenant `arq:dead-letter` list (`saas_os.infra.jobs.dead_letter.purge_tenant_dead_letters_sync()`) as its last step before the final `PURGED` transition — after every PostgreSQL `PURGE_STEPS` pass and every registered `TenantPurgeParticipant` have already succeeded. The removal is a single, atomic, server-side Lua filter (`purge_tenant_dead_letters()`): it keeps any entry belonging to another tenant, any entry with no tenant association (`tenant_id: null`), and any entry it cannot safely interpret, and removes only entries whose `tenant_id` field exactly matches — it can never delete another tenant's data and never loses an entry to a concurrent `RPUSH`/`LTRIM`/another tenant's own cleanup, because Redis executes the whole script without any other command interleaving. It is idempotent (a repeat call finds nothing left and removes 0) and, like every other purge step, **fails closed**: a Redis error here (classified `"redis_cleanup_error"`, bounded, never the underlying exception's message) leaves the tenant `PURGING`, not `PURGED`, and a later retry of `purge_tenant()` re-runs it. The count removed is reported as `TenantPurgeResult.dead_letter_entries_purged` and in the `tenant.purge_completed` audit event's own bounded metadata — never a dead-letter entry's contents. **This is not the same as PostgreSQL's own transactional guarantee, and does not claim to be**: Redis and PostgreSQL share no transaction, so a job that was already queued before the tenant closed can still be picked up by a worker afterward, correctly perform no tenant work (the existing execution-time lifecycle fencing every tenant-associated job handler already has — `require_open_tenant()`/`lock_open_tenant()`), and still write a *new* dead-letter entry naming this tenant *after* the cleanup step has already run, or even after `PURGED` is written. No placement of this step can close that window entirely. That residual exposure is bounded by ARQ's own job-key TTL (~24 hours under the currently pinned ARQ version/configuration, `saas_os/infra/jobs/queue.py`'s own docstring — never refreshed by retries, and the payload key is deleted the instant the job reaches any terminal outcome) and is an explicitly **accepted, bounded limitation**, not a defect this step claims to fix. Queued ARQ job payloads (`arq:job:<id>`) are deliberately **not** scanned or actively cancelled by tenant purge — no tenant-to-job index exists in Redis today, and building one to make that efficient was evaluated and rejected as disproportionate to the marginal benefit over the existing TTL bound and execution-time fencing (RA-12-P7's own design audit). General, time-based dead-letter retention (independent of any specific tenant purge — the list today is bounded only by `JOBS_DEAD_LETTER_MAX_ENTRIES`'s length cap, never by age) remains unsolved by this change and is a separate, still-open policy question, not addressed here.

**Tenant-principal accessibility vs. background-job completion (RA-04, RA-03, RA-12-8).** A tenant's own principals — members, service accounts, API-key holders, and delegates — are denied authorization the instant the tenant is `SUSPENDED`, `DELETED`, `PURGING` or `PURGED` (`saas_os.core.tenancy.lifecycle.PRINCIPAL_INACCESSIBLE_STATUSES`; privacy re-audit finding RA-04). This is enforced, race-safely, at every authorization chokepoint that decides whether a principal may act: `saas_os.core.rbac.can()` (`lock_accessible_tenant()`, re-checked at the target tenant and at every ancestor tenant an ancestor-scoped role or delegation could reach), `saas_os.core.api_keys.validate_api_key()`, and `saas_os.api.dependencies.get_tenant_context()` (a non-enumerating 404, identical to "no such tenant"). `SUSPENDED` is deliberately **not** the same as closed (`CLOSED_STATUSES` = `DELETED`/`PURGING`/`PURGED` only): a suspended tenant's own data may still be mutated by platform, purge and support operations, and support access itself remains reachable while `SUSPENDED` (`lock_open_tenant()`, privacy re-audit finding RA-02) — only its own principals are shut out.

This creates one deliberate, narrower asymmetry, worth stating once rather than only in scattered module docstrings: **a background job already queued while the tenant was open is allowed to complete while the tenant is `SUSPENDED`.** `saas_os.core.notifications`/`saas_os.core.webhooks`/`saas_os.core.usage`'s job handlers re-check the lifecycle at execution time (privacy re-audit finding RA-03) using `require_open_tenant()`/`lock_open_tenant()` — the narrower `CLOSED_STATUSES` fence, not the wider `PRINCIPAL_INACCESSIBLE_STATUSES` one — so a notification, webhook delivery, or usage-event write that was enqueued before suspension still executes and produces its real side effect; the same job is correctly dropped (a silent no-op, never retried or dead-lettered) once the tenant reaches `DELETED`, `PURGING` or `PURGED`. This is intentional, not an oversight: it only ever lets work already in motion finish, it never lets a *new* principal-initiated action begin against a suspended tenant (that path always goes through `get_tenant_context()`/`can()`, both of which deny `SUSPENDED` unconditionally). `tests/core/test_job_lifecycle_fencing_integration.py` carries an explicit regression test for each half of this distinction — completion while `SUSPENDED`, fencing while `DELETED`/`PURGING`/`PURGED` — so the difference stays a locked-in, tested contract rather than an implicit gap.

**Credential issuance is tightened beyond `SUSPENDED` (RA-12-8).** A newly issued credential is authority a principal could exercise later, once the immediate check has passed — so `saas_os.core.api_keys.create_api_key()`, `saas_os.core.api_keys.rotate_api_key()`, and `saas_os.core.identity.create_service_account()` deny `SUSPENDED` too, not merely `CLOSED_STATUSES`: the same RA-04 `PRINCIPAL_INACCESSIBLE_STATUSES` check `validate_api_key()` already enforced at *use* time is now also enforced at *issuance* time for these three paths (`TenantInaccessibleError`, the existing RA-04 exception — no new exception type was introduced). `saas_os.core.api_keys.create_service_account_api_key()` needed no change: it was already gated by its own `saas_os.core.rbac.can()` check, which already denies an ordinary member acting against a `SUSPENDED` tenant. Every other tenant mutation that was already open during `SUSPENDED` (membership creation, role/permission management, invitations, and the background-job completion described above) is unchanged by this — RA-12-8 tightens credential issuance specifically, not the general `require_open_tenant()` mutation policy.

## 7. What Is Hard to Change Later

Restated from the discovery doc because it governs how conservatively Phase 1 must treat this area: **whether tenant scoping is centrally enforced (this document's model) vs. ad hoc is effectively a one-way door.** Once Product code exists that queries the database directly (bypassing `saas_os/infra/db`), retrofitting central enforcement requires auditing and rewriting every such call site under security pressure. The `saas_os/infra/db` chokepoint must exist *before* the first Product query is written, not after.

## 8. Tenant Hierarchy (Structural Only)

Per `docs/ADR/0002-multi-tenancy-isolation-model.md`'s amendment (architecture research: universal multi-tenant tenancy, Phase A):

- A tenant may optionally have a `parent_id` referencing another tenant, forming a strict single-parent tree (never a graph — a tenant has at most one parent). A tenant with `parent_id IS NULL` is a **root tenant**; every tenant created before this feature existed is, and remains, a root tenant.
- `core.tenant_ancestry` is a precomputed closure table (every tenant is its own ancestor at depth 0, plus one row per actual ancestor) maintained transactionally by `saas_os.core.tenancy.service.create_tenant()`/`move_tenant()` — never a recursive query evaluated at request time.
- **Hierarchy is structural data only and grants no authorization by itself.** A parent tenant does not gain access to a child's data, a child does not gain access to a parent's or a sibling's data, merely because `parent_id`/`core.tenant_ancestry` says so. No RLS policy reads `parent_id`/`core.tenant_ancestry` — the isolation model in §2 above (single `app.tenant_id` GUC, one equality policy per table) is completely unchanged by hierarchy existing. `saas_os/core/rbac`'s scoped-role authorization (§9 below) is the one thing that *does* read the live ancestor chain, and only ever to widen or narrow the reach of a role assignment that already requires a real membership, role, and permission grant to exist — it never treats hierarchy membership alone as a grant.
- `move_tenant()` moves the hierarchy relationship (`parent_id` and the moved subtree's `core.tenant_ancestry` rows) only — it never touches any tenant-owned business row. A resource's own `tenant_id` is never rewritten by a move; its history is unaffected.
- A tenant with a living child cannot be deleted/purged (blocked by `parent_id`'s foreign key, not silently cascaded) — reparent or remove every child first.
- Depth is architecturally unbounded (the data model supports arbitrary depth) but operationally guarded by a configurable default (`TENANT_MAX_HIERARCHY_DEPTH`, `saas_os/core/tenancy/config.py`) to keep ancestor-chain size bounded.
- Delegated administration, explicit deny, and a future hierarchy-aware `app.authorized_tenant_ids` RLS GUC remain explicitly deferred future phases (§9 below covers what *is* built: scoped roles).

## 9. Scoped-Role Authorization (SELF / SUBTREE)

Per architecture research: universal multi-tenant tenancy, Phase B ("RBAC + role scope: self, subtree"; `saas_os/core/rbac/scope.py`, `saas_os/core/rbac/authorization.py`):

- Every `MembershipRole` (a role assigned to a tenant membership, `saas_os/core/rbac/models.py`) carries an authorization `scope`: **`SELF`** (the default — the assignment authorizes only the membership's own tenant, the only behavior that existed before this phase) or **`SUBTREE`** (the assignment also authorizes every *current* descendant of the membership's tenant).
- `saas_os.core.rbac.can()` evaluates `SUBTREE` against the **live** `core.tenant_ancestry` closure table (via `saas_os.core.tenancy.get_ancestor_ids()`), never a value captured when the role was assigned — moving a tenant in or out of a subtree (`move_tenant()`, §8) changes what a `SUBTREE` role authorizes immediately, with no rewrite of the `MembershipRole` row itself.
- This does not weaken "hierarchy grants no authorization by itself" (§8): reaching a descendant via `SUBTREE` still requires a real membership, in some tenant along the ancestor chain, with a role, with a permission grant matching the requested `(resource, action)` — `scope` only ever changes *which tenant an already-granted assignment reaches*, never substitutes for the grant itself.
- Database isolation (`app.tenant_id`, RLS) and authorization scope (`SELF`/`SUBTREE`) are deliberately separate concerns: `can()`'s scoped evaluation runs one `tenant_session_scope()`-protected query per candidate tenant in the ancestor chain — never a query spanning more than one tenant's rows, never a second GUC, never a policy change. See `saas_os/core/rbac/authorization.py`'s own docstring for the exact evaluation path.
- Existing installations are unaffected: every `MembershipRole` row that existed before this phase defaults to `SELF` (the migration's `server_default`, never silently widened to `SUBTREE`), and `assign_role()`'s pre-Phase-B call shape (no `scope` argument) still produces exactly that.
