# ADR-0048: Inbound billing-provider events

Status: Accepted (2026-10-15) and implemented — the repository owner approved items 1–8 below as recommended, with a 90-day retention for the ledger.
Date: 2026-10-15
Supersedes / Superseded by: — (closes gap G4 of [ADR-0040](0040-reusable-http-platform-capabilities.md); schedules part of Billing Foundation v2 Phase 6, deferred by [ADR-0029](0029-commercial-parties-and-billing-relationships.md))
Related: ADR-0008 (billing provider; amendment points 5, 6, 8, 9), ADR-0022 (global-by-design `ProviderEvent`), ADR-0030 (route policy), ADR-0031 (callers; the provider-call boundary), ADR-0036 (consumer idempotency), ADR-0041 (extras).

## Context

ADR-0040 left five questions for G4: the ledger and which events change what; the route's policy; provider neutrality; the system authority and tenant resolution; and packaging with the `stripe` extra. Several are already answered by accepted ADRs, which this ADR follows rather than re-decides:

- **ADR-0008, amendment.** Point 5: events are signature-verified, deduplicated by provider event id in a durable ledger, normalized into provider-neutral events and applied idempotently and order-safely. Point 6: correctness never depends on webhooks alone; state can be re-derived from the provider. Point 8: no `stripe.Event` in a Core contract (`verify_stripe_webhook_signature()` was the recorded violation). Point 9: tenant resolution uses SaaS OS's own reference index, never provider metadata.
- **ADR-0022, amendment.** `ProviderEvent` is a global-by-design ledger `(provider, provider_account, event_id UNIQUE, status, …)`; deduplication happens before tenant resolution.
- **ADR-0029.** Event ingestion is Billing Foundation v2 Phase 6, deferred "unless implementation or security review proves [it] a prerequisite".

Facts established while preparing this ADR:

- `reconcile_subscription_status(caller, service_tenant_id=, subscription_id=)` already re-verifies the provider reference, reads the provider's state through the adapter (`get_subscription_status()`, provider-neutral), maps it through the lifecycle (a forbidden transition or `not_found`/`unknown` changes nothing) and applies it in a transaction that re-authorizes and audits. It is idempotent. `SystemCaller(SystemAuthority.BILLING_OPERATIONS)` is accepted by `authorize_billing`.
- `get_subscription_by_provider_ref(provider=, provider_account_ref=, provider_subscription_ref=)` is the bounded cross-tenant lookup through `core.billing_provider_refs`; subscriptions are registered with their merchant's `provider_account_ref`.
- A commercial subscription is written `pending` and becomes `active` only on provider confirmation. Before this ADR that confirmation happened only when someone called `reconcile_subscription_status`: a paid subscription stayed `pending` until then, and a cancellation or failed payment at the provider was not seen.
- Only the platform tenant's merchant has an adapter (Stripe Connect is deferred).
- The HTTP rate limiter is keyed by an arbitrary string; `public_route(reason)` exists for a route with no credential.

## Decision

1. **An event is a notification, not a state.** The handler never applies the state carried in the event body. It extracts the provider subscription reference and calls `reconcile_subscription_status`, which reads the provider's current state. Ordering, duplicates and stale events therefore cannot move a subscription backwards: whatever arrives, the row converges on what the provider says now, through the lifecycle's allowed transitions. This is ADR-0008 point 5's "order-safely" by construction, and it reuses the one audited path that already changes status. No event-type-to-mutation table is needed: an event type is relevant if it names a subscription.
2. **The ledger.** A new global-by-design table, `core.billing_provider_events`: `provider`, `event_id` (unique with `provider`), `event_type`, `provider_account_ref`, `status` (`received`, `processed`, `ignored`, `failed`), `attempts`, `outcome` (why an event was ignored, or whether reconciliation changed anything), `last_error_code` (an exception class name), `processed_at`, and `created_at` (when the event was first received). No payload, no customer data. Registered as global-by-design (ADR-0022) with an allowlisted module. Additive migration.
3. **Processing is synchronous, and the provider's retry is the queue.** In the request: cap the body, verify the signature over the raw bytes, record the event (insert, or find the existing row), then reconcile, then mark the row. If the event is already `processed` or `ignored`, answer `200` without work. If reconciliation fails (provider outage, database error), mark `failed` and answer a `5xx` so the provider redelivers; a redelivery of a `received` or `failed` event is processed again. Because reconciliation is idempotent and re-reads the provider, two concurrent deliveries of one event are harmless, so no lease or lock is held across the provider call (ADR-0031's provider-call boundary).
4. **Tenant resolution.** Only through `get_subscription_by_provider_ref`, for an account of a merchant the platform tenant owns (the event's account when it names one, otherwise each of those accounts). An event that names no subscription, an account the platform tenant does not own (another merchant's, under Connect), or a subscription the index does not know is marked `ignored` and answered `200`. Provider metadata is never read (ADR-0008 point 9).
5. **Authority.** The handler runs as `SystemCaller(SystemAuthority.BILLING_OPERATIONS)`. The audit evidence is the existing `billing.subscription_status_changed` row `reconcile_subscription_status` writes when something changes; receipt itself is evidenced by the ledger, not an audit row.
6. **Provider neutrality.** An adapter-side function translates a verified delivery into a provider-neutral `ProviderEventNotice(provider, event_id, event_type, provider_account_ref | None, provider_subscription_ref | None)`; Core code never sees `stripe.Event`. `verify_stripe_webhook_signature()` stays for compatibility, marked deprecated, and is not the path ingestion uses.
7. **The route.** One opt-in router per adapter: `build_stripe_billing_events_router()`, `POST /v1/billing/providers/stripe/events`, usable only with the `saas-os[stripe]` extra (ADR-0041). It is a `public_route` whose reason is that it is authenticated by the provider's signature over the raw body; it reads the raw body itself (no model parsing before verification), reads no cookie (so the same-origin check has nothing to guard), and is rate-limited under its own key with the deployment's limit; the limiter fails closed (`503`), which the provider retries. The webhook secret comes from the secrets provider (`STRIPE_WEBHOOK_SECRET`); building the router without it fails at startup. Every verification failure is the same `400` with no detail, and is not recorded in the ledger (an unverified id is not trusted).
8. **Scope.** Subscription status only. No invoice mirror (ADR-0008 point 7), no Connect, no product-defined event handlers, no event payload storage.

**Retention (approved with the items above).** Ledger rows are deleted 90 days after they were first received, by a system job. The signature's timestamp tolerance (Stripe: 5 minutes) already refuses old replays; the ledger deduplicates the provider's own redeliveries (Stripe: up to three days).

## Refinements found during implementation

The independent review of the implementation found that item 4, as written, loses events in one race, and that two details of items 3 and 7 needed tightening. These refine the approved items without changing the design:

- **A subscription not known yet is retried, for an hour** (refines item 4). The provider reference and the local row are written only after the provider has created the subscription (`create_subscription`), so `customer.subscription.created` or `invoice.paid` can arrive before SaaS OS knows the subscription. Marked `ignored`, such an event would never be redelivered. Instead, an event naming an unknown subscription is `failed` (`SubscriptionNotYetKnownError`) and answered with a retry for `UNKNOWN_SUBSCRIPTION_GRACE` (1 hour) after it was first received, and `ignored` (`unknown_subscription`) after that, so that subscriptions SaaS OS did not create are not retried for the provider's whole redelivery period. Events that name no subscription or another account are still `ignored` at once.
- **The first run to finish decides** (refines item 3). A terminal mark (`processed`, `ignored`) never overwrites another one, as a `failed` mark never did; a slow concurrent run cannot turn a processed event into an ignored one. A failure to reach the ledger at all is the same retryable failure as any other.
- **The rate limit is per source address** (refines item 7). One bucket for the route would let unsigned requests from anywhere use up the allowance of the provider's own deliveries. The key is `billing-events:stripe:<address>`, the address resolved as for the login rate limit: the direct peer, or the trusted proxy's last `X-Forwarded-For` hop when `TRUST_PROXY_HEADERS` is set.

## Options considered

- **Item 1, notification versus state.** Chosen: notification plus re-read. Rejected: apply the event's state directly with per-object ordering by provider timestamp. It saves the provider call, but needs ordering logic, trusts the event body and duplicates the status path.
- **Item 3, synchronous versus queued.** Chosen: synchronous, the provider's retry as the queue. Rejected for now: record and enqueue a system job, answer `200` at once, with a sweeper for rows left `received`. Faster responses and isolation from provider latency, but it needs a sweeper because the job queue is not transactional with the ledger. Worth it only at volumes this installation does not have.
- **Item 7, path shape.** Chosen: one fixed path per adapter. Rejected: `/v1/billing/providers/{provider}/events` with a registry, while only one adapter exists.
- **Retention.** Chosen: 90 days. Rejected: retaining the rows as financial records; they hold no financial data.

## Consequences

- A paid checkout activates its subscription, and a provider-side cancellation or failed payment is reflected, without anyone calling reconciliation.
- One provider API call per relevant delivery. A provider outage turns into retried deliveries rather than lost events; ADR-0008 point 6 still holds, because on-demand reconciliation remains and the ledger shows `failed` events.
- A product that does not mount the router is unchanged. A product that does must configure `STRIPE_WEBHOOK_SECRET`, register the endpoint with its provider, and install the retention timer.
- New public surface: an unauthenticated route that costs one HMAC per request before rejection, bounded by the body cap and its rate limit.

## Implementation

- **Migration** `a8c3e5f1d204`: `core.billing_provider_events`, unique `(provider, event_id)`, a check on `status` and on `attempts >= 0`, an index on `created_at`. No RLS (global by design, `saas_os/core/tenancy/isolation.py`). The application role keeps the default privileges, `DELETE` included, because the retention job runs as that role; the draft's "`SELECT, INSERT, UPDATE` only" would have left the job unable to prune.
- **Core.** `saas_os/core/billing/provider.py::ProviderEventNotice`; `saas_os/core/billing/provider_events.py::process_provider_event()` (claim, resolve, reconcile, mark), `prune_provider_events()` and `PROVIDER_EVENT_RETENTION`; `saas_os/core/billing/provider_event_jobs.py` registers the retention system job, in a module of its own so that importing `saas_os.core.billing` registers no job. The ledger functions are allowlisted in `tests/architecture/test_tenant_session_boundary.py`, and the `SystemCaller` construction in `tests/architecture/test_authority_contract.py`.
- **Adapter.** `saas_os/core/billing/stripe_provider.py::parse_stripe_event()`: the SDK verifies the signature and timestamp over the raw bytes; the subscription reference is read from a subscription object, from `subscription` (checkout sessions; invoices before Stripe API version 2025-03-31) or from an invoice's `parent.subscription_details.subscription` (since then); the event's `account` names a connected account.
- **HTTP.** `saas_os/api/v1/billing_events.py::build_stripe_billing_events_router(provider=, webhook_secret=)`: rate limit per source address (`billing-events:stripe:<address>`; `saas_os/api/auth/config.py::resolve_client_address`, shared with the login limit), body cap (1 MiB, `413`), signature (`400 invalid_signature`), processing (`200 {"status": ...}`; `503` with `Retry-After` on failure — the draft said `500`; `503` is the repository's existing "try again later" answer and the provider retries either). A verified event Core cannot record (an id longer than the ledger allows) is `400 invalid_event`.
- **Retention.** `python -m saas_os.api.billing_event_retention_trigger` enqueues the job; `deploy/saas-os-billing-event-retention.{service,timer}` run it daily. The worker registers the job (`saas_os/api/worker.py`).
- **Tests.** `tests/core/billing/test_provider_events_integration.py` (activation, audit as the system authority, duplicates without a provider call, a late event that cannot move a subscription backwards, every `ignored` reason including another tenant's merchant, an unknown subscription retried then ignored after the grace, an event that arrives before its subscription is known and is applied on redelivery, outage and redelivery, late failure and late terminal marks that cannot overwrite a finished event, a ledger failure, concurrent deliveries, a malformed notice, retention), `tests/core/billing/test_stripe_event_parsing_unit.py`, `tests/api/v1/test_billing_events_router_integration.py` (signed delivery end to end, redelivery, `503` and redelivery, an unknown subscription retried then ignored, a verified event Core cannot record, every refusal recording nothing, body cap and an unreadable `Content-Length`, a cookie or bearer token granting nothing, the rate limit per source, building without a secret, the public policy), `tests/infra/db/test_billing_provider_events_migration.py`, `tests/api/test_billing_event_retention_trigger_unit.py`.

## Not decided here

- A timeout on the provider call made inside the event's request. *(Since 2026-10-15 the Stripe adapter bounds every call at 15 seconds instead of the SDK's 80.)*

- The invoice mirror, Stripe Connect, and product-defined handlers for other event types (the rest of Billing Foundation v2 Phase 6).
- A queued processing mode, if delivery volume ever needs it.
