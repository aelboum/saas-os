# ADR-0008: Billing provider

Status: Accepted
Date: 2026-09-06
Supersedes / Superseded by: —

## Context

`core/billing` needs a payment-processing and subscription-lifecycle backend. Payment processing carries significant compliance burden (PCI) if built in-house.

## Options Considered

### Option A — Provider-abstraction interface within `core/billing`, with Stripe as the first concrete implementation
- Advantages: near-default choice for SaaS billing; offloads PCI/payment-processing risk entirely; mature subscription/invoicing primitives; keeping Stripe behind an internal interface means Core and Product code never depend on Stripe-specific types, so a future provider swap is an adapter change, not a platform-wide change
- Disadvantages: the abstraction itself is extra design/implementation work up front, since no two billing providers model plans/invoices/entitlements identically

### Option B — Direct Stripe integration (no abstraction layer)
- Advantages: less upfront design work
- Disadvantages: Stripe-specific concepts (its object model, its webhook payloads) leak into Core/Product code, making a future provider change a rewrite rather than an adapter swap

### Option C — Build payment processing in-house
- Advantages: no vendor dependency
- Disadvantages: PCI compliance burden rarely justified for a startup-stage platform; reinvents a solved problem

## Recommendation

Option A.

## Decision

**Accepted.** `core/billing` defines an internal provider-abstraction interface; **Stripe is the first (and initially only) concrete implementation** behind it. The following concepts are modeled as distinct, separately owned sub-concerns within the billing domain — not collapsed into one generic "billing" blob:

| Concept | Owns |
|---|---|
| **Plans** | Product-agnostic plan definitions and their entitlement mappings |
| **Subscriptions** | A tenant's subscription state/lifecycle against a plan |
| **Entitlements** | The product-agnostic "plan → feature/limit" data model (`docs/ARCHITECTURE-DISCOVERY.md` §14) that Product code queries — never provider-specific |
| **Usage** | Owned by `core/usage` (a separate module, `docs/DATA-ARCHITECTURE.md` §6), feeding entitlement/quota checks |
| **Invoices** | Invoice records, generated by or synced from the billing provider |
| **Payments** | Payment transaction records/status, synced from the billing provider |

Only the provider-abstraction layer and its Stripe adapter know about Stripe's specific object model and webhook formats. Plans, Subscriptions, Entitlements, Invoices, and Payments are modeled in provider-agnostic shapes that the Stripe adapter translates into and out of.

## Rejected Alternatives

- **Direct Stripe integration without an abstraction layer (Option B)**: rejected — this platform's core premise is reusability across future products and resilience to vendor changes; letting Stripe's object model leak into Core/Product code directly contradicts that.
- **Build payment processing in-house (Option C)**: rejected — the PCI compliance burden is not justified given a mature, low-friction alternative exists.

## Future Migration / Extension Path

A future additional or replacement billing provider (e.g., Paddle, Chargebee, a regional payment processor) is implemented as a new adapter behind the existing provider-abstraction interface. Because Plans/Subscriptions/Entitlements are already provider-agnostic, Product code that checks entitlements is unaffected by such a change.

## What Would Be Difficult to Change Later

The entitlement-key schema and usage-event schema (`docs/DATA-ARCHITECTURE.md` §6), once Products depend on them for feature gating, are expensive to change regardless of which billing provider sits behind them — this is why they are specified as provider-agnostic from the start, independent of today's Stripe choice.
