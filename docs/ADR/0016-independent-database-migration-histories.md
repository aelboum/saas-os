# ADR-0016: Independent database migration histories for SaaS OS and consuming projects

Status: Accepted
Date: 2026-09-10
Supersedes / Superseded by: —

## Context

ADR-0015 establishes that each consuming SaaS project owns its own physical database, containing both SaaS-OS-owned schema and its own business schema in one instance:

```
Recharge database                MarocAssist database
├── core.*                       ├── core.*
└── recharge.*                   └── marocassist.*
```

`docs/architecture/SAAS-OS-DISTRIBUTION-ARCHITECTURE.md` §6 investigated how migrations against that shared physical database should be owned, discovered, ordered, and executed once `core.*`'s migrations are shipped from a separately-versioned package rather than authored in the same repository as a project's own migrations. This is a materially different situation from today's: currently, all 18 existing Alembic revisions (`infra/db/migrations/versions/`) live in one linear history, applied by one `alembic upgrade head` invocation, because there is exactly one repository and one deployable. Once a second, independent codebase (a consuming project) needs to apply both SaaS OS's core migrations and its own, that single-history assumption no longer holds, and the mechanism must be decided deliberately rather than discovered by accident the first time someone tries.

Two structural facts from direct inspection of this repository shape the options: `infra/db/migrations/env.py` sets `target_metadata = None` — every migration so far is hand-written DDL, not autogenerated, because `infra/db` is architecturally forbidden from importing `core` to build a shared metadata object for diffing (`docs/ARCHITECTURE.md` §2). And the repository already separates a privileged migrations database role (`MIGRATIONS_DATABASE_URL`) from a restricted runtime role (`DATABASE_URL`), because PostgreSQL never applies Row-Level Security to a superuser/BYPASSRLS role.

## Options Considered

### Option A — Single shared Alembic history, multi-root/branched (Alembic's native `version_locations` + branch-label support)
- Advantages: one `alembic upgrade heads` invocation; Alembic natively supports a project migration formally declaring `down_revision` dependence on a specific SaaS OS core revision
- Disadvantages: requires a consuming project's Alembic environment to resolve a script directory living inside an installed package (an extra, less-common path-resolution step); relies on Alembic's branch-label/multiple-heads mechanism, one of the library's less commonly exercised features; the cross-branch dependency it enables is redundant with information the package version pin (ADR-0015) already carries — a project pinning `saas-os==1.4.0` already means "core schema as of 1.4.0's shipped migrations" without needing a second, Alembic-level expression of the same fact

### Option B — Two independent Alembic environments against one physical database
- Advantages: each environment (SaaS OS's core migrations, the project's own migrations) has its own script directory, its own version-tracking table (Alembic's `version_table` option, a standard supported setting), and its own invocation — no shared history to branch or merge; simplest possible mental model, matching the investigation's explicit "how easy is it for one developer to understand" evaluation criterion; because migrations here are hand-written (not autogenerated against one shared metadata object), there is no technical reason the two histories must ever be unified
- Disadvantages: a deploy pipeline must remember to run both migration commands, in the right order; no built-in mechanism to express "this project migration requires core revision X specifically" beyond the package-version pin already providing that guarantee

### Option C — A single, unified database per SaaS OS version, with project data living in a logically or physically separate database entirely (no shared physical database)
- Advantages: total physical separation between `core.*` and project schema
- Disadvantages: contradicts the DB-ownership model already accepted (`docs/DATA-ARCHITECTURE.md`; the prior corrected-architecture audit): a project needs referential integrity from its own tables into `core.tenants` and other core tables via foreign key, which requires them in the same database; splitting into two databases would need cross-database queries or application-level joins for something this simple in a single database, solving a problem that does not exist

### Option D — SaaS OS ships pre-rendered raw SQL migration scripts (no Alembic dependency for the consumer at all), applied by a bespoke runner
- Advantages: removes any dependency on the consuming project also using Alembic
- Disadvantages: reinvents migration-ordering, version-tracking, and rollback machinery Alembic already provides; every consuming project in this codebase's ecosystem already uses the same backend toolchain (ADR-0011: Python/SQLAlchemy/Alembic), so there is no actual heterogeneity to accommodate; strictly more code to build and maintain for no evidenced benefit

## Recommendation

Option B: two independent Alembic environments, one shipped inside the `saas-os` package for `core.*`-owned schema, one owned entirely by the consuming project for its own schema, applied against one shared physical database per project.

## Decision

**Accepted.**

```
Project's physical database (one Postgres instance)

  core.*                              ← owned by SaaS OS
      tracked by:  alembic_version_saas_os
      script dir:  shipped inside the installed saas-os package version
      applied by:  the SaaS OS migration environment

  <project>.*                         ← owned by the consuming project
      tracked by:  alembic_version   (the project's own, ordinary default)
      script dir:  the project's own repository
      applied by:  the project's own, pre-existing Alembic environment
```

Execution order is fixed: **(1) SaaS OS migrations, then (2) project migrations** — core tables (e.g. `core.tenants`, for any foreign key a project table takes into it) must exist before a project migration that references them can run.

Upgrade sequence:

```
1. Bump/pin the saas-os package version
2. Apply SaaS OS's migrations (alembic_version_saas_os advances)
3. Apply the project's own migrations (alembic_version advances)
```

This model is selected over a single shared migration history (Option A) because:

- SaaS OS and each consuming project are independently versioned (ADR-0015) — the package version pin is already the compatibility boundary between them, making a second, Alembic-native cross-branch dependency expression redundant.
- Consuming projects have independent deployment lifecycles (ADR-0015) — nothing about deploying Project X's own migration should require awareness of Project Y's, which two fully independent environments guarantee by construction.
- SaaS OS's current migrations are hand-written, with `target_metadata = None` (`infra/db/migrations/env.py`) — there is no shared autogenerate-diffing metadata object whose fragmentation a single history would otherwise exist to prevent.
- A single multi-root, branch-labeled history introduces coordination machinery (shared version table, branch merges, cross-branch `down_revision` pointers) this scale of problem does not yet need.
- Each project's own physical database already provides isolation between projects — no cross-project migration-state coordination is ever required regardless of which model is chosen.

## Rejected Alternatives

- **Single shared multi-root/branched history (Option A)**: not rejected outright, but not adopted now — a real, viable, Alembic-native alternative, kept as a documented future escalation if a concrete case ever requires expressing "this project migration depends on core revision X specifically," independent of overall package version. No such case has been demonstrated.
- **Physically separate databases per schema owner (Option C)**: rejected — contradicts the already-accepted DB-ownership model requiring cross-schema foreign keys within one database.
- **Bespoke non-Alembic migration runner (Option D)**: rejected — reinvents existing, adequate tooling for no evidenced benefit; every consumer in this ecosystem already uses the same backend toolchain.

## Operational Risks (documented, not resolved by this ADR)

- **Ordering discipline.** A deploy pipeline that runs only the project's own migration command and omits SaaS OS's will silently drift the `core.*` schema behind what the pinned package version expects. This ADR records the required order; it does not build tooling to enforce it.
- **Two-command execution.** Until scaffold/bootstrap tooling exists (ADR-0018, deferred), an operator must run two separate migration commands, in order, by hand or via their own deploy script. This is an accepted, named risk, not a solved one.
- **Partial migration failure.** If SaaS OS's migrations succeed but the project's own subsequently fail (or vice versa), the database is left in a state where one environment's version table has advanced and the other has not. This ADR does not define an automated compensating-transaction or two-phase-commit mechanism across the two environments — each environment's own existing rollback capability (`alembic downgrade`, using each migration's own `downgrade()`, already the convention for all 18 existing revisions) applies independently within its own environment. A full cross-environment rollback strategy beyond this is explicitly not designed here.

## What Would Be Difficult to Change Later

Once consuming projects exist with real production data under this two-environment model, migrating to a unified single-history model (Option A) would require reconciling two independent version-tracking tables into one shared history per already-deployed project database — a real, non-trivial data migration in its own right, not just a tooling change. This is why the model is being decided now, before any real consuming project's database exists, rather than left to be discovered ad hoc by the first project that needs it.

## What Is Deliberately Not Decided Here

- The exact bootstrap/upgrade script or tool that runs both migration commands in order is not built or designed in detail here — only that the two-environment model and the required ordering exist. Building that tooling is future scaffold work (ADR-0018).
- No automated cross-environment rollback/compensation mechanism is designed.
- Whether SaaS OS's core migration script directory is resolved via a package-data path, an `importlib.resources` lookup, or a documented environment variable is an implementation detail left open.
- Single-history multi-root Alembic (Option A) remains an available future escalation, not adopted and not permanently rejected.

## Implementation Note (packaging implementation phase)

Resolves the three items this ADR's own "What Is Deliberately Not Decided Here" left open; does not change the Decision above.

- **`version_table` naming, now fixed.** SaaS OS's own environment (`infra/db/migrations/env.py`) pins `version_table="alembic_version_saas_os"` (both `run_migrations_online()`/`run_migrations_offline()`). A consuming project's own, separate Alembic environment keeps Alembic's ordinary default (`alembic_version`) — exactly the two-name split this ADR's own diagram already showed. `infra/db/backup/__init__.py`'s restore-verification query and its callers were updated to match (they previously queried the literal, soon-to-be-ambiguous name `alembic_version`).
- **Script-directory resolution, now fixed**: `infra.db.migration_runner._MIGRATIONS_DIRECTORY` resolves relative to `infra/db/migration_runner.py`'s own file location (`Path(__file__).resolve().parent / "migrations"`) — correct both in an editable/source-tree install and inside an installed wheel, since `[tool.setuptools.package-data]` ships `infra/db/migrations/` at that same relative path either way. A consumer never resolves this path itself.
- **The bootstrap/upgrade invocation, now built**: `infra.db.migration_runner.run_core_migrations()` (importable) and the `saas-os-migrate upgrade` console script (`infra/db/migration_cli.py`) are the supported ways to apply SaaS OS's own migration history — in-process, via `alembic.command`, never a shell subprocess. Both proven end-to-end against a real, disposable PostgreSQL instance, and via `examples/reference-consumer/` (ADR-0018) running SaaS OS's migrations followed by its own, separate migrations against one shared database, asserting both `alembic_version_saas_os` and `alembic_version` exist independently.
- **Operational risk mitigation.** §16/"Operational Risks"'s "two-command execution" risk is now partly mitigated: a project still runs two commands (SaaS OS's via `saas-os-migrate upgrade`, its own via its own `alembic upgrade head`), but neither requires knowing an installed package's internal filesystem layout any more.
